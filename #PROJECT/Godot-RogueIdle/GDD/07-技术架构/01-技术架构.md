# Godot 实现边界与依赖顺序

状态：v1 设计约束，**不表示现有工程已经实现**。项目编辑规范统一见 [AGENTS.md](../../AGENTS.md)。

## 1. 当前工程事实

HTML MVP是独立原型；cat-idle 与 rogue-idle-gd 是两个独立工程，本次未迁移、合并或改代码。下一次实施先依据具体任务确认目标工程、实际Godot版本和主场景，再落地本规范。不把旧技术报告中的文件创建结果当作引擎内运行、编辑和存档验收。

## 2. 四层分工

| 层 | 职责 | 禁止 |
|---|---|---|
| 静态配置 | 区域、单位、技能、效果、装备、事件、主题与多边形 Resource | 写入当前生命/冷却等本局状态 |
| 规则域 | RunState、BattleState、活动事务、战斗推进、奖励生成 | 依赖动画帧率、节点点击次数来判定结果 |
| 应用协调 | 场景切换、存档、配置加载、种子、输入命令验证 | UI绕过校验直接改AP/金币 |
| 表现 | 可编辑场景、地图块、卡片、特效、日志播放器 | 重写另一套伤害或掉落算法 |

最小常驻服务只承担配置加载和存档/当前远征协调。战斗状态是独立实例，避免把全部系统塞进一个Autoload。先用直接接口和语义信号，不为M1构建任意插件式框架。

## 3. 状态边界

远征状态：村庄 → 区域整备 → 活动进行/战斗 → 待领奖 → 区域整备 → 最终整备 → 最终战 → 局后结算。

一切命令必须校验所在状态。未解决事件、未领取战利品、进行中战斗不能移动或再开活动；免费查看信息可以。新开局必须处理覆盖进行中远征的提示。

输入命令例：MoveToRegion、ConfirmActivity、ChooseEventOption、ChangeLoadout、ClaimReward。它们返回成功后的新状态与领域事件，或带原因的失败；扣费失败不能留下半次修改。

## 4. 依赖顺序

1. CSV校验与配置资源 → 确定性战斗及回放事件。
2. 小队属性与装备/套装 → 三类敌人意图 → 战前策略。
3. 地图、区域与内容生成 → 活动事务 → 掉落/事件。
4. 完整远征状态机 → 存档恢复 → 可编辑UI与反馈。
5. 真人试玩 → 平衡修订 → 内容扩展 → Steam发布准备。

实施可交错搭建占位UI，但没有规则测试就不能用界面看起来正常作为系统完成。必须始终能跑一条端到端路线。

## 5. 数据工作流

CSV是平衡数据源，导入到对应自定义Resource用于Inspector查看、引用和运行；导入器是待开发任务。正式调参只编辑CSV并重新生成，Inspector试验用副本，确认后回写CSV。场景布局、多边形坐标、主题、音量和动画参数直接由Godot资源/Inspector维护，不需要塞进数值CSV。

检查引用、整数范围、ID唯一、循环依赖、每轮触发上限。所有保存的战斗快照带规则版本；规则变更后的旧局不按新数值静默继续。
