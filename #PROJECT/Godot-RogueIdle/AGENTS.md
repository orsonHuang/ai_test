# Godot-RogueIdle 项目文件夹编辑规范

生效日期：2026-10-04。状态：用户要求执行的项目约定。

## 1. 适用范围与优先级

- 本文只约束 `#PROJECT/Godot-RogueIdle/` 项目文件夹及其全部子目录中的工作，包括文档、策划、素材、代码、场景、资源、原型和工具的新增、编辑、整理与交付。它不是工作区全局规范，不适用于其他项目。
- 文件夹编辑通则适用于所有任务；后文的 Godot、MCP 与引擎验收要求仅在相关开发任务中适用。修改 GDD 或 HTML 原型时，不强制执行无关的 Godot 操作。
- 每次开始项目工作，先阅读根目录 `README.md`、本文，以及目标工程和功能的相关说明；不能只凭上轮聊天记忆继续开发。
- 用户最新明确指令优先于本文。本文约束本项目文件的编辑和工程实现；玩法细节以用户已确认决策及相应设计文档为准，旧 GDD 不得覆盖后续已确认的变更。
- 子目录规则可以补充具体约定；不得自行取消本文的可编辑性、持久化和真实验收要求。发现实际冲突时说明影响，继续不受影响的工作。
- 日常实现、可逆修复和已授权范围内的验证直接推进，不因本规则重复索要许可。必要的技术例外需记录原因、范围、替代方案和验证结果，不得默默降低交付标准。

## 2. 项目文件夹编辑通则

- **先读后改**：修改文件前读取其当前内容及相关引用，确认本次编辑的目的、归属和影响范围；不得直接覆盖未知内容。
- **修改范围**：本项目任务默认在本文件夹内完成。不得因为更新本项目，就附带修改工作区全局规范、全局索引、其他项目或全局工具配置；跨目录写入需要明确任务依据。
- **目录保持**：保留 `Godot-RogueIdle` 及现有目录名称，不为绕开工具路径问题改名、搬迁整个项目或新建第二套相同目录。多个子工程之间不自动复制、覆盖或同步。
- **文件归属**：按下表存放内容，编辑已有内容时优先更新原文件，不制造同主题、状态不明的重复版本。

| 目录/文件 | 编辑用途 |
|---|---|
| `README.md` | 项目入口、目录索引、当前状态与运行方式 |
| `AGENTS.md` | 本项目唯一主编辑规范 |
| `GDD/` | 玩法、系统、数值、配置结构与已确认设计 |
| `docs/` | 脑暴、方案比较、技术说明、验证记录等辅助资料 |
| `project-plan/` | 任务、阶段范围、依赖、里程碑与验收进展 |
| `html-mvp/` | HTML 原型及其说明、测试，不代表 Godot 工程实现 |
| `cat-idle/`、`rogue-idle-gd/` | 各自独立的 Godot 工程，按任务明确目标后修改 |
| `参考图/`、`素材包/` | 参考与素材来源；保留原件和授权说明，处理后的游戏素材放入目标工程 |

- **设计文档**：区分用户已确认、待讨论、历史方案与实现现状。需求变更时更新对应系统文档及受影响的引用，不将脑暴或测试假设直接写成既定规则。
- **源码和素材**：保留用户及其他任务的未提交改动；二进制原图、素材包和独立候选不直接覆写为处理结果。文件删除、移动或批量替换不得超出明确任务范围。
- **索引和链接**：新增重要文件、子工程或入口时，更新本项目 README 或对应目录说明；项目内 Markdown 使用可解析的相对链接。重命名或移动时同步引用，检查断链。
- **编辑质量**：沿用已有编码、换行、术语和格式；只整理本次涉及部分。说明与代码、数据或工程实际状态一致，不进行无关的全文件重排。
- **验证与提交**：文档检查内容、链接和差异；代码与场景检查对应功能。只提交本项目内本次任务所属文件，不使用会带入整个工作区改动的批量提交方式。
- **项目记录**：本项目的决策、状态和交付说明优先维护在本目录的 README、设计文档、计划或验证记录中，不以写入全局记忆文件作为本项目编辑的必要收尾动作。

## 3. Godot 开发目标与工程入口

- 正式产品采用 Godot 4.x，目标平台为 Steam。HTML 用于玩法验证，不能以浏览器原型通过替代 Godot 工程交付。
- 开始修改前，确认实际目标工程路径、`project.godot`、主场景、引擎版本和 Git 工作区状态。存在多个工程时，结合任务与入口说明确定目标，不按文件夹新旧自行迁移或覆盖。
- 引擎版本以实际可执行程序及工程配置共同核对；升级引擎、渲染器或插件不作为普通功能开发的默认附带操作。
- 已有用户改动、其他任务生成的工程、参考图和第三方插件均需保留。只修改和提交本次任务所属文件，不做顺手清理或跨工程批量格式化。
- 旧实现不因本文生效而自动触发全量重构；新功能和本次实际修改的部分必须遵守，存量差异需据实说明。

## 4. Godot 交付标准：在引擎内继续可视化编辑

**交付后，用户必须能在 Godot 编辑器中打开相关场景，在场景树中选中节点，通过 Inspector 调整其公开属性，并保存、重开和运行。**

- 页面、面板、角色卡、战斗单位、地图块等可复用视觉组件必须有真实的 `.tscn` 场景与合理的节点层级；脚本负责行为、数据绑定和必要的动态实例化。
- 固定 UI 使用 `Control`、容器、标签、按钮、纹理等原生节点。禁止把整页 UI 仅在 `_ready()` 中临时构建，或把交互界面做成一张不能逐元素编辑的大图来充当正式交付。
- 战斗生成的怪物、随从、奖励卡、随机地图块等，优先实例化可编辑的 `PackedScene` 模板。运行时数量、位置、状态可由脚本决定，不要求把每个运行时实例预先保存到场景中。
- 程序化地形、绘制效果或特效确需脚本生成时，提供可编辑的源参数、资源及预览方式；不能声称运行时临时节点已经是可保存的编辑器场景节点。
- 地图分区、布局、主题样式和关键图形参数应能通过节点或资源调整。编辑器需要预览生成结果时，选择受控的预览场景或必要的 `@tool`，避免编辑器加载时执行游戏存档、战斗或破坏性操作。
- UI 排版优先使用容器、锚点、尺寸约束和 Theme；需要绝对位置的地图等布局可使用坐标，但坐标和形状数据必须有明确可编辑来源。
- 节点名称表达用途，类名和节点名采用 `PascalCase`。可复用组件保留场景实例关系，修改共享组件时区分源场景修改和单个实例覆盖。
- 编辑器新增节点必须设置正确的 `owner`，确保能保存。不得为图省事递归覆盖实例子节点的所有权、展开整个子场景或破坏继承关系；确有需要时按 Godot 的可编辑子节点/实例覆盖机制处理。
- 不得在运行开始时无条件重写本应由用户配置的布局、主题或初始参数。动态行为会接管某属性时，应在导出参数或组件说明中明确其控制方式。

## 5. Godot 数据、脚本与场景分工

- GDScript 使用 Godot 4.x API、显式类型、`snake_case` 变量和方法、`UPPER_SNAKE_CASE` 常量、语义明确的信号。项目自有新增脚本采用 4 空格缩进；修改已有文件保持其缩进一致，不混用或批量重排第三方源码。
- 不确定的 API 查对应引擎版本的官方文档或 ClassDB，不能凭其他引擎或语言的习惯编造接口。
- 可调参数使用 `@export`，并按用途使用分组、枚举或范围提示；不得把策划和美术需要调整的数值散落为魔法数字。
- 装备、词条、技能、效果原子、套装、敌人和区域内容采用自定义 `Resource` 与 `.tres` 等可检查的配置。沿用项目已有的效果原子复用原则，避免在技能、装备和套装中重复写同一规则。
- 区分静态配置与本局状态。生命、行动点、掉落结果、技能冷却等不得直接写回共享的资源模板；需要可变副本时显式创建运行时状态或复制资源。
- 战斗规则、远征状态与 UI 展示分离。核心计算应能在不依赖动画播放、帧率或点击频率的情况下验证；表现层订阅事件或读取状态，不另写一套结算规则。
- 场景尽量自包含，通过信号、明确接口及传入数据协作。减少 Autoload，不把所有玩法、UI、存档和资源管理塞进一个全局脚本。
- 场景、脚本、资源、美术和工具按功能组织；游戏资源使用 `res://`，用户存档使用 `user://`。不得把开发机器绝对路径写进运行时资源引用。

## 6. MCP 与编辑器协作

- 优先复用项目已有且版本配套的 Godot MCP。选型、安装、启用、连通和实际操作通过是不同状态，报告中必须区分。
- 使用 MCP 前先进行只读检查：编辑器版本、目标工程、当前场景与场景树。确认正在操作正确工程后，再修改节点或属性。
- 编辑器插件、MCP 服务端与客户端配置需要版本配套；记录所用版本和启动方式，不能把新版服务端配置直接套在旧插件上。
- 场景和节点修改优先通过 Godot 原生编辑器 API。支持的节点增删、属性修改应进入原生 UndoRedo；保存、文件写入等不能撤销的操作，通过清晰的文件差异与 Git 保持可追溯。
- 创建真实场景实例，保存节点所有权、脚本绑定、资源引用、信号与布局。不得只在运行中的远程场景树上修改后，就称编辑器源场景已经更新。
- 首次接入或更换版本后，用独立验证场景检查：读场景树 → 创建节点 → 改属性 → 保存重开 → 验证撤销 → 运行与截图。不要把验证节点混进正式页面。
- 编辑器中存在未保存改动时，不强制重载或从磁盘覆盖。避免编辑器和外部文件工具同时修改同一份场景；可转用独立验证场景或不冲突的文件继续工作。
- MCP 暂时不可用时，允许继续脚本、资源或 `.tscn` 的文件工作，并进行可执行的无头检查；恢复编辑器后仍须补做可视化与持久化验收，不能提前宣称已通过。
- 插件更新优先采用其支持的安装/迁移流程，不把新旧插件目录直接混合覆盖。第三方工具与游戏业务代码分开维护。

## 7. 当前玩法实现约束

- 保持已确认方向：主角加最多两名随从、全自动回合战斗、相邻向前选路、战争迷雾、有限区域探索预算、首领装备驱动构筑。改动这些方向需有用户的新指令依据。
- 回合制战斗中，速度决定行动顺序；额外行动如要引入，必须是明确的玩法机制，不能由表现动画或计时误触发。
- 揭雾生成的区域内容、本局随机结果、活动是否完成、行动点扣除和战利品领取均需有明确状态。刷新 UI、读档或重开面板不得重抽内容、重复扣费或重复领奖。
- 免费换装和阵位调整、跨区生命延续等规则由同一份状态逻辑执行，避免界面显示与实际结算不一致。
- 本文不永久锁死原型数值、装备槽位数或内容量。调整时同步相关设计/原型说明和受影响验证，不把测试样例中的暂定数值当成不可修改的产品规则。

## 8. 验证与完成条件

按本次改动选择必要检查，不为纯文字修改运行全量游戏测试；出现新失败或风险后再扩大检查范围。

| 改动类型 | 必须提供的验证 |
|---|---|
| 场景、节点、Inspector 参数 | 在正确工程打开，查看层级与属性；保存并重开，确认节点、值和资源绑定仍存在 |
| 可复用/继承场景 | 确认实例引用没有被展开或破坏；区分共享源修改与实例覆盖，检查代表性使用处 |
| UI、地图、视觉布局 | 引擎内截图及实际交互；检查目标窗口尺寸、文字、遮挡、点击与缩放；无头通过不能替代视觉验收 |
| 战斗、行动点、掉落、存档 | 运行对应规则验证或可复现流程，覆盖主要边界；确认重入、保存恢复不会重复结算 |
| MCP 接入或版本变化 | 执行独立场景的连通、编辑、撤销、保存重开、运行截图验证 |
| 发布/导出 | 检查目标导出预设、资源路径和产物运行；确认调试/MCP 桥接不会在正式构建中提供开发控制入口 |

- 对需要用户手动调节的代表性参数，做一次「Inspector 调整 → 保存 → 重开 → 运行观察」验证；测试结束恢复有意保留的交付值。
- 查看 Godot 的脚本解析、运行错误和与改动相关的警告。功能需要状态联动时，不能仅凭节点出现或截图正确判定完成。
- 测试需要可执行入口和真实结果；不要报告没有运行的测试，也不要将模拟通关结果当成真人难度验证。
- 环境限制导致某项检查无法运行时，明确已验证、未验证和具体阻塞点；继续完成不依赖该条件的工作，不把未完成项标为通过。

## 9. 文档与交付

- 新增重要场景、资源目录、工具或运行方式，更新项目/工程 README 的入口索引；规则以本文为唯一主文档，其他入口链接本文，避免多份副本逐渐冲突。
- 交付时说明：改了什么、应打开哪个工程/场景、哪些参数可在 Inspector 调节、做了哪些验证，以及尚未完成的部分。
- 只提交本次任务所属变更。保留他人的未提交改动、独立候选、旧版备份和验证资料；不把与任务无关的清理合入提交。
- 后续调整本规则时，同步本文件与相关入口，写明变更原因；用户已作出的明确决定不反复询问。
