# 战斗系统设计流程 · 逐步拆解

> 面试话术适用：当面试官问"你怎么设计一个战斗系统"，用这个流程从头讲到尾，展示你的**系统化思维**，而不是零散的"做过XX"。

---

## 第 1 步：立项 → 战斗风格定位

### 思路
在动笔前先定调。战斗风格是产品的 DNA，决定之后每一步的取舍。定错风格 = 后面全部返工。

### 三个核心决策

**① 轻重度**（决定操作复杂度）
```
超轻：点一下出技能，半自动战斗（放置/挂机/三消）
轻量：双键操作，有明确技能时机（荒野乱斗、皇室战争）
中度：3-4 个技能 + 方向操作（王者荣耀、原神）
重度：6+ 个技能 + 搓招 + 连段（DNF、鬼泣）
```

**② 动作/策略比**（决定玩家靠手还是靠脑）
```
纯策略：回合制，无实时操作（炉石、杀戮尖塔）
策略偏重：慢节奏即时，决策>操作（皇室战争、自走棋）
均衡：操作和决策并重（王者荣耀、荒野乱斗）
动作偏重：操作碾压策略（DNF、猎天使魔女）
```

**③ 目标玩家画像**（决定门槛和深度）
```
泛用户：15 秒学会上手，爽感即时（消消乐）
轻度竞技：2 分钟一局，输了不气（荒野乱斗）
中核：有操作门槛，但天花板不至于劝退（王者荣耀）
硬核：练习 100 小时才入门（DNF 决斗场、街霸）
```

### 举例（你的简历映射）
- Zodiac Heroes：**轻量 × 策略偏重 × 轻度竞技**——三消降低操作门槛，卡牌技能提供策略空间
- Hero of Taslinia：**中度 × 纯策略 × 中核**——回合制但天赋/技能形态深
- 光汇这个岗位：大概率是**轻中量 × 均衡 × 轻度竞技**（休闲竞技方向）

### 输出物
- 一页战斗风格定位文档，含：轻重度 / 动作策略比 / 目标玩家 / 3 款对标竞品 / 2 个差异化点

## 第 2 步：核心循环设计

### 思路
战斗不是一个技能接一个技能，而是一个**闭环循环**。这个循环决定了"玩家在战斗中每分钟在做什么"。

### 战斗核心循环公式
```
移动 → 侦查/试探 → 决策 → 交技能 → 反馈 → 重置 → 移动...
```

### 三个关键指标

**① 单局时长目标**
```
< 90 秒：超休闲竞技（荒野乱斗单场 2-3 分钟）
90-180 秒：轻中度竞技（皇室战争 3 分钟+加时）
3-5 分钟：中核 MOBA（单次团战，非整局）
> 10 分钟：重核（DOTA2 40 分钟）
```
**时长的设计约束**：时长越短，CD 必须越短、死亡惩罚必须越小、操作密度必须越高。

**② 攻防比**
```
进攻主导型：攻方优势大，鼓励主动（MOBA 刺客、FPS）
均衡型：攻防对等（王者荣耀常规对线）
防守主导型：守方优势大，鼓励阵地战（塔防、末日生存）
```

**③ 技能资源分配**
先定总资源池，再分给每个技能：
```
资源模型 A：能量制（统一蓝条/能量条，各技能共享）
资源模型 B：CD 制（每个技能独立冷却，无统一资源）
资源模型 C：充能制（攻击命中/时间自动充能，大招独享）
资源模型 D：混合（普通技能 CD + 大招充能）
```

### 举例
> 设计一个轻量级休闲竞技手游：
> - 单局 **120 秒**（2 分钟到点结算，加时 30 秒）
> - 攻防比 **6:4**（偏进攻，鼓励主动打架，不鼓励蹲坑）
> - 资源模型：普通技能 **CD 制**（3/5/8 秒），大招 **命中充能**（打中一次充 20%，满 5 次可放）
> - 循环节奏：前 30 秒试探 → 30-90 秒激战期 → 90-120 秒残局收尾

### 输出物
- 单局节奏曲线图（纵轴=操作密度，横轴=时间）
- 技能资源分配表

## 第 3 步：战斗公式建模

### 思路
数值不是后补的，是和风格同时定下来的。战斗公式决定了**什么属性有价值**、**装备系统怎么做**、**平衡好不好调**。

### 基础伤害公式（三大模型）

```
模型 A：减法公式
Dmg = ATK - DEF
特点：简单直观，但 DEF 过高时破不了防 → 必须控制 DEF 上限
适用：回合制 RPG（你的 Hero of Taslinia）

模型 B：百分比减伤（最常见）
Dmg = ATK × (1 - DEF/(DEF + K))
特点：DEF 永不完全免疫伤害，K 值控制减伤曲线
适用：MOBA、ARPG、大部分即时战斗

模型 C：乘区隔离（最灵活）
Dmg = ATK × SkillCoeff × (1+增伤%) × (1-减伤%) × (1+易伤%) × 暴击修正 × 浮动(0.95~1.05)
特点：每个乘区独立，调一个乘区不影响其他 → 最易平衡
适用：MOBA、重度 ARPG
```

### 独立结算模型（你简历里做过的，重点讲）
```
Hero of Taslinia 的技能有 3 段伤害，每段独立判定：
- 第 1 段：命中判定 → 是 → 暴击判定 → 否 → 伤害
- 第 2 段：命中判定 → 否 → miss（独立于第 1 段）
- 第 3 段：命中判定 → 是 → 暴击判定 → 是 → 暴击伤害

好处：
1. 段数越多，越接近期望值（方差小）
2. 每段反馈独立，打击感好（每下都飘字）
3. 可以给不同段打不同特性（第1段减速、第2段破甲、第3段斩杀）
```

### 延迟生效公式（控制/位移/治疗）
```
控制时长 = 基础时长 × (1 - 韧性%)，下限 0.3 秒
位移距离 = 基础距离 × (1 + 移速加成%)，受碰撞体积阻挡
治疗量 = 基础治疗 × (1 + 治疗加成%) × (1 - 重伤%)
```

### 举例
> 假设设计一个轻量竞技手游的标准伤害公式：
> ```excel
> =ATK * Coeff * (1 - DEF/(DEF+200)) * (1+PassiveBonus) * IF(RAND()<CritRate, 1+CritDmg, 1)
> ```
> - K=200：当 DEF=200 时减伤 50%，DEF=400 时减伤 67%
> - 这条曲线的美感：前期叠防收益高（0→200 直接 50%），后期收益递减（200→400 只加 17%），玩家不会无脑堆防御

### 输出物
- Excel 战斗公式表（带公式 + 带曲线图）
- 属性价值评估表（1 点 ATK 价值 vs 1 点 CritRate 价值）

## 第 4 步：技能结构设计

### 思路
技能不只是"一个技能"。它是一个**完整的数据结构**，每个字段都在战斗中有实际意义。设计时先定结构，再定内容。

### 技能字段标准表

| 字段 | 类型 | 说明 | 举例 |
|---|---|---|---|
| SkillID | int | 唯一标识 | 10001 |
| SkillName | string | 策划名（非最终） | "烈焰突刺" |
| SkillType | enum | 主动/被动/大招/连携 | Active |
| SkillLevel | int | 技能等级（成长） | 1-5 |
| DamageCoeff | float | 伤害系数（×ATK） | 1.5 |
| HealCoeff | float | 治疗系数 | 0 |
| CD | float(秒) | 冷却时间 | 6.0 |
| EnergyCost | float | 能量消耗 | 30 |
| CastTime | float(秒) | 施法时间（前摇） | 0.3 |
| ActiveFrames | float(秒) | 伤害判定帧窗口 | 0.15 (第 0.3-0.45 秒) |
| Recovery | float(秒) | 后摇 | 0.4 |
| Range | float | 作用距离 | 8.0 |
| RangeShape | enum | Circle/Sector/Rect/Chain | Sector |
| RangeAngle | float | 扇形角度 | 60° |
| TargetType | enum | Enemy/Ally/Self/Ground | Enemy |
| MaxTargets | int | 最多目标数 | 3 |
| ControlType | enum | 击退/浮空/减速/眩晕/无 | 击退 |
| ControlDuration | float(秒) | 控制时长 | 0.8 |
| DeriveSkillID | int | 派生技能 ID | 10002（第 2 段） |
| VFX_ID | string | 特效资源 | "fx_fire_dash" |
| SFX_Hit | string | 命中音效 | "sfx_fire_hit" |
| HitFreeze | float(ms) | 顿帧时长 | 60 |
| CameraShake | float | 震屏强度 0-1 | 0.3 |
| CanBeInterrupted | bool | 是否可被打断 | false |
| InvincibleFrames | float(秒) | 无敌帧时长 | 0 |
| SuperArmor | bool | 霸体 | false |

### 设计时的三步检查

**检查 1：这个技能在「资源-风险-收益」三角里自洽吗？**
```
高伤害 + 长 CD + 长后摇 + 可被打断 = 高风险高收益（合理）
高伤害 + 短 CD + 无后摇 + 不可打断 = 数值怪物（垃圾设计）
```

**检查 2：这个技能的「空间感」对吗？**
```
近战短距离 + 扇形 = 群战敢死队
远程长距离 + 弹道 = 后排输出
全图 + 延迟命中 = 炮台（需要预判）
```

**检查 3：这个技能有「反制手段」吗？**
```
闪避能躲？护盾能扛？净化能解？霸体能顶？
如果 4 个都是"不能"→ 这是必中技能 → 这只能是大招，否则没法玩
```

### 举例（你的简历映射）
> Hero of Taslinia 的"技能形态"就是在这个结构上加了**形态切换**字段：
> - 形态 A：单体高伤 + 吸血
> - 形态 B：AOE + 减速
> - 形态切换 CD：2 回合
> - **设计意图**：让同一个英雄面对单体 BOSS 和群怪有两种解法，而不是逼玩家换英雄

### 输出物
- 技能字段标准表（Excel，每行一个技能）
- 技能资源-风险-收益三角自查表

## 第 5 步：战斗规则（状态机 + 优先级表）

### 思路
战斗规则是战斗系统的"法律"。当两个技能同时生效时，谁说了算？这不能靠代码拍脑袋，必须有一张**优先级表**。

### 核心状态

```
┌──────────────────────────────────────────────┐
│              Idle（待机）                      │
│    ↙ ↓ ↘                                      │
│ Move  Cast   BeHit                           │
│  ↓     ↓       ↓                              │
│ Move  Active  Stun/Float/Knockback/Down      │
│         ↓       ↓                              │
│       Recovery  Recovery（硬直结束自动回 Idle） │
│         ↓                                     │
│        Idle                                   │
└──────────────────────────────────────────────┘
```

### 控制效果优先级表（最关键的一张表）

**原则**：高优先级覆盖低优先级，同优先级后发覆盖先发。

| 优先级 | 控制类型 | 可否叠加 | 说明 |
|---|---|---|---|
| 0 | 无 | - | 正常状态 |
| 1 | 减速 | 是（取最大） | 多个减速取最大值 |
| 2 | 沉默 | 是（取最大时长） | 禁止使用技能 |
| 3 | 定身 | 否 | 不可移动但可普攻 |
| 4 | 眩晕 | 否 | 不可操作 |
| 5 | 击退 | 否 | 强制位移+硬直 |
| 6 | 浮空 | 否 | 可接空中连段 |
| 7 | 击飞 | 否 | 浮空+位移 |
| 8 | 冻结/石化 | 否 | 最高级硬控 |
| → | **霸体** | 免疫 1-5（但不免疫位移） | |
| → | **无敌** | 免疫全部 | |

### 护盾 / 无敌 / 霸体的交互规则

| 交互 | 霸体 | 无敌 | 护盾 |
|---|---|---|---|
| 被眩晕 | 免疫眩晕 | 免疫 | — |
| 被击退/浮空 | **仍然被位移** | 免疫 | — |
| 受到伤害 | 全额吃 | 0 伤害 | 先扣盾 |
| 吃到 DoT | 全额吃 | 0 伤害 | 先扣盾 |
| 可被驱散 | 是 | 否 | 是 |

### 举例（你简历里的 Hero of Taslinia）
> 战斗操作优化中的**行动条指示器**就是战斗规则的可视化：
> 1. 谁先动 → 行动条排序
> 2. 我打谁 → 可选目标高亮（免疫目标灰色）
> 3. 我打到谁 → 选中目标 + 作用范围标出受影响的敌方
> 4. **规则的本质**：让玩家在行动前就知道"我能做什么"，而不是行动后才发现"怎么打不了"

### 输出物
- 状态转换图（一张 A4 纸）
- 控制优先级表（Excel，用条件格式标色）
- 交互矩阵表（护盾×控制、无敌×位移 等交叉验证）

## 第 6 步：表现层（打击感的工程化落地）

### 思路
表现层不是"让美术做炫一点"——是策划用**精确的数值**告诉美术和程序：在哪个时刻、给什么反馈、强度多少。**顿帧不是感觉，是 ms 数。**

### 五维落地表

```
┌────────┬──────────────────┬─────────────────────┐
│  维度   │  策划要给的参数    │  执行方              │
├────────┼──────────────────┼─────────────────────┤
│ 顿帧   │ 命中冻结 X ms      │ 程序：Time.timeScale │
│        │ 出手方/受击方分别设 │                     │
├────────┼──────────────────┼─────────────────────┤
│ 震屏   │ 强度 0-1 / 衰减曲线 │ 程序：Camera Shake   │
│        │ 持续时间 / 方向     │                     │
├────────┼──────────────────┼─────────────────────┤
│ 镜头   │ FOV 变化值 / 推拉量  │ 程序：Camera Zoom    │
│        │ 触发帧 / 恢复时长   │                     │
├────────┼──────────────────┼─────────────────────┤
│ 特效   │ 命中点坐标 / 颜色    │ 美术：VFX 预制体     │
│        │ 大小 / 持续时间     │                     │
├────────┼──────────────────┼─────────────────────┤
│ 音效   │ SFX 标签 / 优先级   │ 音效：分层播放        │
│        │ 音量 / 淡入淡出     │                     │
├────────┼──────────────────┼─────────────────────┤
│ 飘字   │ 字体大小 / 颜色     │ 程序：DamagePopup    │
│        │ 弹跳曲线 / 停留     │                     │
├────────┼──────────────────┼─────────────────────┤
│ 受击   │ 受击动画 / 时长     │ 美术：HitReaction    │
│ 反应   │ 方向 / 强度/位移    │                     │
└────────┴──────────────────┴─────────────────────┘
```

### 顿帧分级表（重点记）

| 攻击类型 | 顿帧时长 | 感觉 |
|---|---|---|
| 普攻轻击 | 0-20ms | 几乎无感，保持流畅 |
| 普攻重击 | 30-50ms | 有分量，但不卡顿 |
| 技能命中 | 50-80ms | "砰"的一下，明显打击感 |
| 大招 / 处决 | 100-150ms | 重击级冲击，"时间凝固"感 |
| 致命一击 | 150-200ms | 仅终结技，超过 200ms 会觉卡 |

**关键原则**：出手方和受击方的顿帧时长可以不对称。出手方 30ms（有反馈但不影响操作），受击方 80ms（感受被揍的沉重）。

### 举例（你的简历映射）
> 3D 足球的**子弹时间系统**就是表现层的节奏控制：
> 1. 射门瞬间 → timeScale 降至 0.3，持续 1.5 秒
> 2. 镜头从侧面推近到球的特写
> 3. 球入网瞬间 → timeScale 恢复正常 + 震屏 0.5
> 4. **设计意图**：用 1.5 秒的减速放大"这一脚决定胜负"的戏剧感，比直接进球多给玩家 10 倍的情绪峰值

### 输出物
- 打击感参数配置表（Excel，每行一个技能，含所有表现参数）
- 顿帧分级标准文档

## 第 7 步：数值平衡

### 思路
平衡不是"凭感觉调数字"，而是**先建模、再跑模拟、再 AB 测试**。每一轮都是"假设→数据→调整"的闭环。

### 三步平衡法

**Step 1：自检表（上线前，Excel 完成）**

对每个技能/英雄，跑以下检查：
```
[ ] DPS 是否在设定区间内？（偏差 > 20% = 重做）
[ ] 爆发峰值是否合理？（1 秒内输出 > 目标 60% 血量 = 超标）
[ ] CD 是否与 DPS 自洽？（DPS×CD 应该和资源消耗成正比）
[ ] 是否有反制窗口？（无 = 加后摇或可打断）
[ ] 极端场景：满 CDR 堆叠会不会无限连？满暴击会不会一刀秒？
[ ] 与其他技能的配合有没有 1+1>3 的乘法爆炸？
```

**Step 2：胜率模型（内部模拟）**

```
英雄 A 在段位 X 的胜率：
  = (对 B 胜率 × B 出场率) + (对 C 胜率 × C 出场率) + ...

目标：50% ± 3%
过高（>55%）→ 微砍系数 5-10%
过低（<45%）→ 微加系数 5-10%，或给机制补强
```

**Step 3：AB 测试（上线后，灰度放量）**

```
单一变量原则：每次只动 1-2 个数值
分两组（10% vs 10% 灰度玩家）
观察 3 天数据：
  - 胜率变化
  - 使用率变化（强了都抢用）
  - 对局时长变化
  - 玩家投诉/论坛舆情
```

### 单局时长模型

```
预估时长 = 双方总血量 / (双方 DPS × 命中率)
实际时长 = 预估 × 操作系数（躲技能/走位稀释输出，通常 1.3-1.8 倍）
```

如果目标是 120 秒，双方 DPS 设计值 = 双方总血量 / (120 / 1.5) ≈ 总血量/80。

### 举例
> Hero of Taslinia 竞技场优化：
> - 之前匹配算法只看等级，导致高等级玩家碾压低等级 → 低等级留存暴跌
> - 改进：匹配权重 = 等级(30%) + 近期胜率(40%) + 战力(30%)
> - 结果：匹配质量提升，低等级玩家胜率从 35% 恢复到 48%
> - **教训**：平衡不只是调技能系数，**匹配算法也是平衡的一部分**

### 输出物
- 英雄 DPS 对比表（雷达图）
- 胜率/出场率监控表（每周更新）
- AB 测试记录模板

## 第 8 步：程序对接

### 思路
策划和程序之间的鸿沟是"感觉 vs 逻辑"。你要做的不是让程序理解你的感觉，而是**用程序能理解的语言描述你的设计**。

### 策划要能讲清的四样东西

**① 状态机（让程序不用猜"什么时候能放技能"）**
```
策划输出：状态转换图 + 转换条件表

例：
Idle → Cast_Skill_10001
  条件：CD=0 AND Energy>=30 AND NOT Silence AND NOT Stun

Cast_Skill_10001 → Active_Skill_10001
  条件：CastTime 计时结束（0.3s）

Active_Skill_10001 → Recovery
  条件：ActiveFrames 计时结束（0.15s）

Recovery → Idle
  条件：RecoveryTimer 计时结束（0.4s）
```

**② 动画帧事件（告诉程序和美术"什么时刻出伤害"）**
```
策划输出：技能时间轴

| 时刻 | 事件 |
|------|------|
| 0ms  | 开始前摇动画 |
| 200ms| VFX_Charge 开始播放 |
| 300ms| → 伤害判定帧 ← （程序在这里算伤害）|
| 300ms| SFX_Hit 播放（音效在这里触发）|
| 300ms| 顿帧 80ms 生效 |
| 380ms| 顿帧结束，后摇开始 |
| 450ms| VFX_Hit 命中特效播放 |
| 700ms| 后摇结束，回 Idle |
```

**③ 技能配置数据（ScriptableObject / 策划配表）**
```
策划输出：数据表结构定义

class SkillData {
    int id;           // 技能 ID
    float coef;       // 伤害系数
    float cd;         // 冷却时间
    float castTime;   // 前摇
    float activeFrames; // 判定帧时长
    float recovery;   // 后摇
    // ... 全部字段（见第 4 步的技能字段表）
}
```

**④ 事件广播（告诉程序"哪些事发生后要通知其他系统"）**
```
策划输出：事件列表

OnSkillCast(skillID, casterID)
  → UI 更新 CD 显示
  → 任务系统：释放技能 N 次

OnSkillHit(skillID, casterID, targetID, damage, isCrit)
  → 战斗日志
  → 成就系统：造成暴击 N 次
  → 教学系统：首次造成暴击

OnUnitKilled(killerID, victimID, skillID)
  → 击杀播报
  → 连杀系统
  → 任务/通行证进度
```

### 举例
> 你简历里的 "竞技场匹配算法 + 机器人生成算法" 就是程序对接产物：
> - 策划输出的是**需求文档**（匹配权重公式、机器人行为规则）
> - 程序实现的是**代码逻辑**（ELO算法、机器人状态机）
> - 你中间做的是**桥梁**：用程序能理解的伪代码描述策划意图

### 输出物
- 状态机 Visio 图
- 技能帧事件时间轴表
- ScriptableObject 字段定义文档
- 事件广播协议表

## 第 9 步：内测调优

### 思路
内测不是"找人玩然后问好不好玩"。是**用数据和观察验证之前的假设**，找出"设计意图 vs 实际体验"的偏差。

### 四个调优维度

**① 数据调优（看数字）**
| 指标 | 目标值 | 问题信号 |
|---|---|---|
| 单局时长 | 120±15 秒 | < 90s：太碾压；> 180s：太墨迹 |
| 技能使用率 | 每局 5+ 次 | < 2 次：CD 太长或技能太废 |
| 命中率 | 60-80% | < 40%：太难命中；> 95%：无脑 |
| 死亡次数 | 1-3 次/局 | 0 次：太无趣；> 5 次：太挫败 |
| 连杀率 | 5-15% 局有 | 太高：平衡崩了 |

**② 手感调优（看录像/自己玩）**
```
观察：
- 玩家命中后多久才下一次操作？（hit-tap latency）
  → > 500ms 说明打击反馈不够爽，顿帧或音效需加强
- 玩家躲技能的动作频率？
  → 太低说明技能不明显/太慢；太高说明太紧张
- 玩家在什么时刻最兴奋？（看录像表情或操作频率峰值）
```

**③ 平衡调优（看胜率/出场率）**
```
高胜率 + 高出场率 = 数值超标 → 砍系数
高胜率 + 低出场率 = 只有绝活哥用 → 可能不用动
低胜率 + 高出场率 = 玩家喜欢但不够强 → 微加强
低胜率 + 低出场率 = 设计失败 → 加机制还是重做？
```

**④ 体验调优（看玩家反馈）**
```
玩家说的 ≠ 玩家真正需要的。

玩家说："这个英雄太弱了"
真相可能是："我玩不明白这个英雄" 或者 "这个英雄的定位写错了"

玩家说："战斗太无聊"
真相可能是："操作密度太低" 或者 "反馈不够" 或者 "决策太简单"
```

### 调优闭环
```
假设 → 改参数 → 小范围灰度测试 → 看数据 → 验证/推翻假设 → 再调整
```

### 举例
> Zodiac Heroes 战斗框架优化（你的实际经验）：
> - **问题**：三消棋子掉落有延迟，卡牌技能释放时机难以和消除同步
> - **假设**：给卡牌技能加一个 0.5 秒的"预输入窗口"
> - **测试**：灰度 5% 玩家
> - **结果**：技能命中率从 55% 提升到 72%，单局时长从 150 秒降到 120 秒
> - **结论**：预输入窗口有效，全量上线

### 输出物
- 内测数据看板（每日更新 5 个核心指标）
- 玩家录像分析记录（每周 10 场重点局）
- 调优日志（每次改了什么、为什么改、改了之后数据变化）

## 第 10 步：上线监控（战斗数据看板）

### 思路
上线不是终点，是战斗系统真正开始被"大量玩家用各种想不到的方式玩"的时候。你的任务是**在数据崩之前发现问题**。

### 战斗数据看板（必须监控的指标）

**核心指标（每日看）**
```
┌─────────────┬──────────┬──────────────────┐
│   指标       │  阈值     │  超标后动作       │
├─────────────┼──────────┼──────────────────┤
│ 单局平均时长  │ 目标±20% │ 检查平衡/匹配质量  │
│ 各英雄胜率   │ 50%±5%   │ >55%=削, <45%=补 │
│ 各英雄出场率  │ 目标±30% │ <2%=调查原因      │
│ 各英雄被禁率  │ <10%     │ >20%=紧急平衡     │
│ PVP匹配时长  │ <30秒    │ >60秒=加机器人   │
│ 战斗崩溃率   │ <0.1%    │ >0.5%=紧急修复    │
│ 技能命中率   │ 60-80%   │ 超范围=调查       │
│ 玩家投诉率   │ <1%      │ 飙升=查版本改动   │
└─────────────┴──────────┴──────────────────┘
```

**深度指标（每周看）**
```
- 新玩家 vs 老玩家的英雄偏好差异（预判"哪个英雄新手玩不懂"）
- 各段位 Meta 分布（防"全段位都用同一个英雄"）
- 连杀/连败分布（检查是否有匹配漏洞）
- 战斗内付费道具使用率（平衡商业化）
- 版本更新前后 7 天对比（验证调整效果）
```

### 紧急预案

| 事故等级 | 条件 | 处理 |
|---|---|---|
| **P0 紧急** | 英雄胜率 > 65% 或 < 30%，持续 24h | 紧急热更，系数砍/加 20% |
| **P1 重要** | 匹配时长 > 90s，或崩溃率 > 1% | 48h 内发补丁 |
| **P2 观察** | 某英雄出场率 < 1% | 下个版本加强 |
| **P3 记账** | 舆情负面但数据正常 | 回复玩家 + 观察 2 周 |

### 举例（你的简历映射）
> 你在腾讯广点通做的**游戏分析 + CP 反馈**就是数据监控的雏形：
> - 从大盘数据中看这款游戏的付费/留存/时长
> - 发现某游戏某关卡的**流失率异常高**（30% 玩家在这里退出）
> - 反馈给 CP："关卡 27 难度曲线断了，建议削 20% 敌人血量"
> - **这和战斗数据看板是同一种能力**——从数据中找问题，给出可执行的调优方案

### 输出物
- 战斗数据看板（线上 Dashboard）
- 每周战斗健康报告（邮件/文档）
- 紧急预案手册（谁负责、多久响应、怎么热更）

## 面试时可以说的"金句"

- "战斗设计不是画完流程图就完的事。从风格定位到公式建模、从帧事件到表现层参数，每一个环节我都要知道**交给程序的是什么数据、交给美术的是什么参数**。"

- "我不写代码，但我能写出程序可以直接翻译成代码的**状态转换条件表**。这是我计算机背景的差异化价值。"

- "打击感不是感觉，是**顿帧的毫秒数 + 震屏的强度曲线 + 音效的分层优先级**。策划要给出精确数字，不是形容词。"

- "平衡的本质不是让所有英雄一样强，是让每个英雄在**自己该强的地方强、该弱的地方弱**，而且玩家能看懂为什么。"
