## 问题：关卡数据放在哪，谁拥有它？

状态：user_confirmed

### 广度分析

- **候选 A · 全部打进包体（本地 JSON/resource）**：
  能提供：零网络依赖、加载最快、实现最简单。
  但会带来：4MB 主包限制下放不下几百关；每次更新关卡都要重新提审。

- **候选 B · 全部远程加载（CDN / 云开发）**：
  能提供：关卡量无上限；内容更新不提审；可做 A/B 与热修。
  但会带来：首次加载需网络；需处理缓存、版本、失败降级。

- **候选 C · 混合：前 N 关内置 + 其余远程**：
  能提供：首屏零等待（教学关必定可玩，无网络也能玩前几关）；后续内容远程化。
  但会带来：需要维护两套加载路径；内置关卡占用包体需精算。

- **候选 D · 远程 + 启动时全量预拉取到本地缓存**：
  能提供：运行时零网络依赖，体验等同本地。
  但会带来：首次启动需下载全部关卡（几百关 JSON 虽小，但仍是一次网络请求）；关卡量增长后首次加载变慢。

### 深度分析

判断标准是：**微信小游戏的两条硬约束（4MB 包体、提审周期）如何一次性解决，且不影响玩法？**

逐条排除：
- 候选 A 直接违背"绝不打进包体"的项目规则，排除。
- 候选 D 的问题在于关卡量增长：500 关 JSON 压缩后可能几 MB，首次全量拉取会拖慢启动，而**启动速度是小游戏留存的第一杀手**。
- 候选 B 是标准解法，但首屏依赖网络——如果玩家在弱网/离线打开，第一关都进不去。

候选 C 是唯一同时满足两者的：
- **前 20–30 关（教学 + 首段）内置**——保证任何网络状态下都能立即开玩，且这部分手工设计、体积小（几百 KB 级别）
- **其余全部远程**——关卡量无上限，更新不提审
- **按批次懒加载 + 本地缓存**——玩到哪下到哪，首次启动成本最小

数据所有权：关卡系统**独占**关卡数据的读写。其他系统只能通过关卡 ID 请求，不得自行持有或缓存网格内容。

### 综合判断

**采用候选 C：前 20–30 关（手工设计的教学与首段）内置于包体，其余全部远程按批次懒加载 + 本地缓存。**

- **数据所有权归关卡系统独占**；其他系统只能通过关卡 ID 请求，不得持有网格内容。
- 远程加载失败时的降级策略：优先使用本地缓存；无缓存则回退到内置关卡池。
- 关卡 JSON 格式设计见 `03_systems/S02_level/`。

## 问题：求解器与生成器放在哪——运行时、离线工具，还是两者都有？

状态：user_confirmed

### 广度分析

- **候选 A · 仅离线工具**：生成器与求解器是独立的 node 脚本，产出的关卡 JSON 上传 CDN，游戏运行时完全不含求解逻辑。
  能提供：包体最小；运行时性能零开销；工具可用最强的算法（无需考虑小游戏环境）。
  但会带来：游戏内"提示"功能无法实现（需要运行时求解）。

- **候选 B · 仅运行时**：游戏内内置求解器，关卡在运行时生成。
  能提供：无限关卡，零内容存储。
  但会带来：小游戏端算力有限，穷举求解会卡顿；关卡质量不可控（无法预先筛选难度）；"每日挑战全服同题"无法实现。

- **候选 C · 离线生成 + 运行时轻量求解（仅用于提示）**：离线用强求解器批量生成并验证；运行时只保留一个受限深度的求解器，用于提示功能。
  能提供：内容质量可控 + 提示功能可用；运行时求解可限深限时不卡顿。
  但会带来：需要维护两套求解实现（离线与运行时）。

- **候选 D · 离线生成 + 提示使用预存解法**：关卡 JSON 中直接存一条参考解；提示功能直接展示预存解的下一步。
  能提供：运行时零求解开销；提示功能实现最简单；包体/流量增加极小（每关多存十几个方向）。
  但会带来：提示只能给"标准答案"，不能给"基于玩家当前局面的建议"。

### 深度分析

判断标准是：**提示功能需不需要"基于当前局面"？**

本游戏的每一步都是不可逆的。玩家卡住时，通常不是在"下一步怎么走"上卡住，而是在"开局路线规划"上出错。
这意味着：给"基于当前局面的下一步"很可能**没用**——因为玩家已经走错了，当前局面可能已无解。

真正有用的提示是两种：
1. **给一条完整参考解的下一步**（提示玩家标准路线）
2. **直接告诉玩家"这关已经无解了，重开吧"**（止损提示）

候选 D 恰好完美覆盖这两种，且运行时零开销：
- 预存解 → 提示下一步
- 运行时只需做一次轻量的"是否还有解"判断（可用简化剪枝的 DFS，或直接对比玩家路径是否偏离预存解）

候选 C 的运行时求解器是过度设计。

另外，候选 D 还有一个隐藏收益：**预存解可用于校验玩家是否被卡死**，这是"止损提示"的基础。

### 综合判断

**采用候选 D：生成器与求解器作为离线工具（node 脚本），产出的关卡 JSON 内嵌一条参考解；运行时不实现求解器。**

- 提示功能直接读取预存解的下一步。
- 「是否还有解」的判断通过**玩家路径与预存解的偏离检测**实现，不做运行时穷举。
- 离线工具与运行时的滑行核心**共用同一份 TypeScript 规则代码**（`core/` 层不依赖 Cocos），保证离线验证与运行时行为完全一致。

## 问题：网格循环如何工程化——静态配置、动态计算，还是生成器参数？

状态：user_confirmed

### 广度分析

- **候选 A · 静态配置表**：在关卡数据或配置文件中硬编码每关的网格尺寸（如 `level_1: small, level_2: small, level_3: medium...`）。
  能提供：最直观，策划可直接调整节奏。
  但会带来：关卡量大时维护成本高；新增关卡需要手动指定尺寸。

- **候选 B · 动态计算（按序号取模）**：根据关卡序号动态计算网格尺寸（如 `sizeIndex = levelIndex % 10`，映射到小/中/大）。
  能提供：零配置，关卡生成器自动遵循节奏；新增关卡无需额外处理。
  但会带来：节奏固定，无法灵活调整（如想临时加一段"全大网格"挑战关需要改代码）。

- **候选 C · 生成器参数化**：生成器接受"节奏模板"参数（如 `[small, small, medium, medium, medium, large, large, large, large, large]`），生成关卡时按模板分配尺寸。
  能提供：节奏可配置，生成器自动遵循；模板可热更新。
  但会带来：需要设计模板格式与解析逻辑。

- **候选 D · 混合（动态计算 + 模板覆盖）**：默认按序号取模，但支持配置模板覆盖默认节奏。
  能提供：默认零配置，特殊需求可覆盖。
  但会带来：两套逻辑并存，可能产生混乱。

### 深度分析

判断标准是：**网格循环的本质是什么？**

网格循环是**节奏设计**，不是关卡内容。它的目的是让玩家体验"热身→深入→挑战→重置"的节拍。

候选 B（动态计算）最简洁：
- 关卡序号确定 → 网格尺寸确定
- 生成器只需知道当前关卡的序号，自动分配尺寸
- 无需额外配置，无需维护映射表

候选 A 的问题是维护成本：100+ 关的关卡池，每关都要手动指定尺寸，容易出错。

候选 C 的灵活性在本项目中不必要：节奏是固定的 10 关循环，没有"临时调整"的需求。

候选 D 的复杂度收益不对等。

### 综合判断

**采用候选 B：动态计算，按关卡序号取模确定网格尺寸。**

节奏公式：
```
sizeIndex = levelIndex % 10
if sizeIndex < 2: small
elif sizeIndex < 5: medium
else: large
```

- 关卡生成器自动遵循此节奏。
- 无需额外配置，新增关卡无需手动指定尺寸。
- 若未来需要调整节奏，修改公式即可。

## 问题：进度持久化由谁持有，如何存储？

状态：user_confirmed

### 广度分析

- **候选 A · 关卡系统自行持久化**：关卡系统存储当前关卡进度、每关星级。
  能提供：职责清晰，关卡相关数据集中管理。
  但会带来：若未来加入成就系统，成就数据无处安放。

- **候选 B · 统一存档层，各系统只提供序列化片段**：一个持久化服务收集各系统的状态快照，统一写入。
  能提供：原子写入、版本迁移集中处理、便于加云存档。
  但会带来：多一层抽象；各系统需实现序列化接口。

- **候选 C · 关卡进度归关卡系统，成就归成就系统，但都由统一存档层调度**：
  能提供：数据所有权清晰（谁的状态谁定义）+ 写入一致性（统一调度）。
  但会带来：MVP 阶段成就系统未实现，存档层可能过度设计。

- **候选 D · 全部状态集中在一个全局 store**：
  能提供：读写最简单。
  但会带来：数据所有权完全模糊，违背架构铁律；多人协作必冲突。

### 深度分析

判断标准是：**MVP 阶段需要多复杂的持久化方案？**

MVP 只有两个系统：滑行核心 + 关卡。需要持久化的状态：
- 当前关卡序号（进度）
- 每关星级评价（成就/收集的基础）

这些数据量小、结构简单，关卡系统可以独立管理。

但若未来加入成就系统、社交系统，数据所有权会分散，需要统一存档层保证一致性。

**MVP 阶段采用候选 A（关卡系统自行持久化），但预留存档层接口**，未来扩展时平滑迁移到候选 C。

### 综合判断

**采用候选 A（MVP）：关卡进度与星级由关卡系统自行持久化。**

- MVP 只需存储：当前关卡序号、每关星级。
- 预留存档层接口，未来成就/社交系统接入时迁移到统一存档层。
- 存储方式：微信小游戏本地存储（`wx.setStorage`），未来可扩展云存档。

## 问题：呈现层要不要单列一个 GDD 系统？

状态：user_confirmed

### 广度分析

- **候选 A · 单列「信息呈现系统」**：
  能提供：UI/可读性有明确责任方。
  但会带来：本游戏信息量极小（一屏网格 + 星级），单列系统是形式主义。

- **候选 B · 不单列，呈现归执行文档**：
  能提供：GDD 聚焦规则与结构，避免文档膨胀。
  但会带来：可读性这一核心体验无人认领。

- **候选 C · 不单列系统，但在架构层声明「呈现契约」**：不设系统，但明确规定"呈现层只读状态、不做规则判断、不替玩家解题"，并在各系统的「不负责」清单中写明边界。
  能提供：守住"呈现与规则分离"的铁律，又不增加冗余系统。
  但会带来：呈现契约散落在各处，需要 GDD/README 集中索引。

- **候选 D · 单列，但归入 P1**：MVP 不写，等 UI 复杂后再补。
  能提供：MVP 精简。
  但会带来：可读性从第一天就是核心，等不起。

### 深度分析

判断标准是：**规范铁律「呈现与规则分离」的目的是什么？**

这条铁律的真实目的是防止两件事：
1. 呈现层偷偷做规则判断（导致规则不可测试、离线验证失效）
2. 呈现层替玩家解题（如自动高亮可行路径、自动排除无效方向）

这两条对本游戏**极其重要**：
- 第 1 条：如果渲染层做了"哪些格子可走"的判断，那么离线求解器的验证结论就与运行时不一致——**内容护城河直接崩塌**
- 第 2 条：本游戏的核心乐趣就是自己推演路径。任何"帮你排除无效方向"的辅助都是**在削掉核心玩法**

因此铁律必须守，但实现方式不必是单列一个系统——本游戏的信息呈现没有需要"决策"的内容，它只是**渲染 + 只读展示**。

候选 C 是正确的：把约束写成**契约**，在架构层集中声明一次，在各系统的「不负责」清单中落实。

特别需要契约锁死的一条：**禁止"自动排除无效方向"类的辅助**。
（即：不允许在 UI 上把"推不动的方向"置灰，或在滑动时阻止玩家输入。玩家必须能自己撞墙、自己发现走不通——这是学习过程的一部分。）

### 综合判断

**采用候选 C：不单列呈现系统，在架构层集中声明「呈现契约」，并在各系统的「不负责」清单中落实。**

呈现契约三条：
1. 呈现层**只读取状态**，不做任何规则判断。
2. 呈现层**不替玩家解题**——不自动高亮可行路径、不预测滑行结果、不排除无效方向。
3. 具体 UI 布局、美术规格、动效归执行文档与美术文档，GDD 不承载。

## 问题：MVP 的系统边界如何切，什么必须进 P0？

状态：user_confirmed

### 广度分析

- **候选 A · 两个系统（核心 + 关卡）**：只做 Longcat 本体。
  能提供：最快出可玩版本，验证核心手感。
  但会带来：无任何差异化，验证的其实是 Longcat 而非本项目。

- **候选 B · 核心 + 关卡 + 社交（最小形态）**：加入每日挑战 + 分享。
  能提供：完整验证"社交比拼 + 滑行填充"这个核心假设。
  但会带来：MVP 工作量较大，社交系统需要后端支持。

- **候选 C · 核心 + 关卡 + 成就（最小形态）**：加入星级评价 + 基础图鉴。
  能提供：留存钩子，"我在慢慢积累"的情绪价值。
  但会带来：无社交，无法验证裂变假设。

- **候选 D · 四个系统（核心 + 关卡 + 社交 + 成就）**：
  能提供：完整闭环。
  但会带来：MVP 严重超范围。

### 深度分析

判断标准是：**MVP 要验证的核心假设是什么，最少需要哪些系统？**

核心玩法验证只需要：滑行核心 + 关卡。

但项目定位是"社交比拼 + 滑行填充"，完整验证需要社交系统。

考虑到资源限制与 Top Design 结论（"先做 A，后续迭代社交内容，需要预留接口"），**MVP 只做两个系统，但必须预留社交接口**。

预留接口包括：
- 关卡成绩记录接口（为排行榜准备）
- 分享回调接口（为分享奖励准备）
- 每日关卡生成接口（为每日挑战准备）

这些接口在 MVP 不实现具体逻辑，但数据结构与调用方式必须定义好，后续迭代可直接对接。

### 综合判断

**采用候选 A：MVP 只做滑行核心 + 关卡，后续迭代社交内容。**

**必须预留接口**：
- 关卡成绩记录（星级、步数、用时）
- 分享回调
- 每日关卡生成

P1 迭代时加入：每日挑战、好友排行榜、分享奖励、成就图鉴。
