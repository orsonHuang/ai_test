## 问题：能力如何作用于核心规则——参数化注入、规则分支，还是事件钩子？

状态：agent_proposal

### 广度分析

- **候选 A · 参数化注入（modifier）**：滑行核心预定义一组可调参数（如 `allowReverse`、`allowCrossBody`、`maxUndo`、`cancelSlide`），能力只修改这些参数的值。
  能提供：核心规则代码零分支、可测试性最强、新增能力不改核心；能力效果可组合（多个能力同时生效即参数叠加）。
  但会带来：能力的设计空间被参数集限制，想不出参数表达的能力就做不了。

- **候选 B · 规则分支（if ability_X then ...）**：核心结算时检查能力集，走不同分支。
  能提供：任何能力都能实现，无表达力限制。
  但会带来：核心代码被能力污染，每加一个能力都要改核心；分支组合爆炸（N 个能力有 2^N 种组合），无法测试。

- **候选 C · 事件钩子（hook）**：核心在关键节点发事件（滑行前/滑行后/判负前），能力注册监听器修改结果。
  能提供：表达力强于参数化，弱于分支；核心代码保持干净。
  但会带来：监听器顺序影响结果，调试困难；能力间可能产生隐式冲突（两个能力同时改同一步）。

- **候选 D · 混合（参数化为主 + 钩子逃生舱）**：常规能力走参数，极少数特殊能力走钩子。
  能提供：兼顾干净与表达力。
  但会带来：两套机制并存，长期可能退化成"大家都用钩子"，参数化被架空。

### 深度分析

判断标准是：**上游要求"能力单向注入"且"规则层与回收层分离"，哪种机制能真正守住这条边界？**

候选 B 直接违背上游结论——核心感知能力概念，规则层被回收层污染。排除。
候选 C 表面上核心不感知能力，但监听器能任意修改结果，等于把规则判断权外包出去了，**实质是隐性耦合**。且"监听器顺序影响结果"会让关卡的可验证性失效——求解器无法模拟全部能力组合下的行为。

这是一个被低估的风险：**如果能力能任意改变滑行结果，那么"关卡 100% 可解"的保证就只成立于无能力状态**。
而上游要求的是"关卡与能力解耦，能力只降低难度"——这意味着**能力必须不能让关卡变得无解**。

候选 A（参数化）天然满足这一点：如果所有参数都是"放宽约束"型（允许回头、允许撤销、允许穿身），那么任何能力组合下，关卡的解集都只会变大、不会变小。
**这是一个可以用数学保证的性质：无能力可解 ⇒ 任意能力组合下也可解。**

候选 A 的表达力限制反而是优点——它强制能力设计者往"放宽约束"的方向想，而这正是能力应有的定位（降低难度，不构成通关前提）。

关于候选 D 的退化风险：本项目不采用。若将来出现参数无法表达的能力，正确做法是**扩充参数集并重新校验**，而不是开钩子逃生舱。

### 综合判断

**采用候选 A：能力以「规则修正参数（modifier）」的形式单向注入滑行核心，核心代码零能力分支。**

硬约束：
- **所有 modifier 必须是「放宽约束」型**——任何能力组合下，关卡的解集只会变大不会变小。这保证了「无能力可解 ⇒ 任意能力组合下可解」的数学性质。
- modifier 由能力系统计算并汇总，滑行核心只接收参数对象，**不感知能力概念本身**。
- 若某能力无法用现有参数表达 → 扩充参数集并重新校验，不引入钩子或分支。

## 问题：关卡数据放在哪，谁拥有它？

状态：agent_proposal

### 广度分析

- **候选 A · 全部打进包体（本地 JSON/resource）**：
  能提供：零网络依赖、加载最快、实现最简单。
  但会带来：4MB 主包限制下放不下几百关；每次更新关卡都要重新提审。

- **候选 B · 全部远程加载（CDN / 云开发）**：
  能提供：关卡量无上限；内容更新不提审；可做 A/B 与热修。
  但会带来：首次加载需网络；需处理缓存、版本、失败降级。

- **候选 C · 混合：前 N 关内置 + 其余远程**：
  能提供：首屏零等待（教学关必定可玩，无网络也能玩前几关）；后续内容远程化。
  但会带来：需要维护两套加载路径；内置关卡占用包体需精算。

- **候选 D · 远程 + 启动时全量预拉取到本地缓存**：
  能提供：运行时零网络依赖，体验等同本地。
  但会带来：首次启动需下载全部关卡（几百关 JSON 虽小，但仍是一次网络请求）；关卡量增长后首次加载变慢。

### 深度分析

判断标准是：**微信小游戏的两条硬约束（4MB 包体、提审周期）如何一次性解决，且不影响玩法？**

逐条排除：
- 候选 A 直接违背"绝不打进包体"的项目规则（`#PROJECT/longcat/README.md` 工作规则 4），排除。
- 候选 D 的问题在于关卡量增长：500 关 JSON 压缩后可能几 MB，首次全量拉取会拖慢启动，而**启动速度是小游戏留存的第一杀手**。
- 候选 B 是标准解法，但首屏依赖网络——如果玩家在弱网/离线打开，第一关都进不去。

候选 C 是唯一同时满足两者的：
- **前 20–30 关（教学 + 首章）内置**——保证任何网络状态下都能立即开玩，且这部分手工设计、体积小（几百 KB 级别）
- **其余全部远程**——关卡量无上限，更新不提审
- **按章节懒加载 + 本地缓存**——玩到哪下到哪，首次启动成本最小

数据所有权：关卡系统**独占**关卡数据的读写。其他系统（run、局外）只能通过关卡 ID 请求，不得自行持有或缓存网格内容。这符合规范架构铁律「数据所有权唯一」。

### 综合判断

**采用候选 C：前 20–30 关（手工设计的教学与首章）内置于包体，其余全部远程按章节懒加载 + 本地缓存。**

- **数据所有权归关卡系统独占**；其他系统只能通过关卡 ID 请求网格，不得持有网格内容。
- 远程加载失败时的降级策略：优先使用本地缓存；无缓存则回退到内置关卡池（具体策略归执行文档）。
- 关卡 JSON 格式设计见 `03_systems/S02_level/`。

## 问题：求解器与生成器放在哪——运行时、离线工具，还是两者都有？

状态：agent_proposal

### 广度分析

- **候选 A · 仅离线工具**：生成器与求解器是独立的 node 脚本，产出的关卡 JSON 上传 CDN，游戏运行时完全不含求解逻辑。
  能提供：包体最小；运行时性能零开销；工具可用最强的算法（无需考虑小游戏环境）。
  但会带来：游戏内"提示"功能无法实现（需要运行时求解）。

- **候选 B · 仅运行时**：游戏内内置求解器，关卡在运行时生成。
  能提供：无限关卡，零内容存储。
  但会带来：小游戏端算力有限，穷举求解会卡顿；关卡质量不可控（无法预先筛选难度）；"每日挑战全服同题"无法实现。

- **候选 C · 离线生成 + 运行时轻量求解（仅用于提示）**：离线用强求解器批量生成并验证；运行时只保留一个受限深度的求解器，用于提示功能。
  能提供：内容质量可控 + 提示功能可用；运行时求解可限深限时不卡顿。
  但会带来：需要维护两套求解实现（离线与运行时）。

- **候选 D · 离线生成 + 提示使用预存解法**：关卡 JSON 中直接存一条参考解；提示功能直接展示预存解的下一步。
  能提供：运行时零求解开销；提示功能实现最简单；包体/流量增加极小（每关多存十几个方向）。
  但会带来：提示只能给"标准答案"，不能给"基于玩家当前局面的建议"。

### 深度分析

判断标准是：**提示功能需不需要"基于当前局面"？**

拆解研究表明 Longcat 的一个明显缺陷是"无提示"。本项目把提示作为留存与变现工具（广告变现点）。

但注意：**本游戏的每一步都是不可逆的**。玩家卡住时，通常不是在"下一步怎么走"上卡住，而是在"开局路线规划"上出错。
这意味着：给"基于当前局面的下一步"很可能**没用**——因为玩家已经走错了，当前局面可能已无解。

真正有用的提示是两种：
1. **给一条完整参考解的下一步**（提示玩家标准路线）
2. **直接告诉玩家"这关已经无解了，重开吧"**（止损提示，比让玩家继续挣扎体验好得多）

候选 D 恰好完美覆盖这两种，且运行时零开销：
- 预存解 → 提示下一步
- 运行时只需做一次轻量的"是否还有解"判断（可用简化剪枝的 DFS，或直接对比玩家路径是否偏离预存解）

候选 C 的运行时求解器是过度设计。

另外，候选 D 还有一个隐藏收益：**预存解可用于校验玩家是否被卡死**，这是"止损提示"的基础。

### 综合判断

**采用候选 D：生成器与求解器作为离线工具（node 脚本），产出的关卡 JSON 内嵌一条参考解；运行时不实现求解器。**

- 提示功能直接读取预存解的下一步。
- 「是否还有解」的判断通过**玩家路径与预存解的偏离检测**实现，不做运行时穷举。
- 离线工具与运行时的滑行核心**共用同一份 TypeScript 规则代码**（`core/` 层不依赖 Cocos），保证离线验证与运行时行为完全一致。这是架构铁律的直接收益。

## 问题：run 状态与局外进度由谁持有，如何持久化？

状态：agent_proposal

### 广度分析

- **候选 A · 各系统自行持久化**：run 系统存 run 状态，局外系统存解锁进度，关卡系统存章节进度。
  能提供：职责清晰，各存各的。
  但会带来：存档一致性无法保证（中断时部分写入）；多处读写存储 API。

- **候选 B · 统一存档层，各系统只提供序列化片段**：一个持久化服务收集各系统的状态快照，统一写入。
  能提供：原子写入、版本迁移集中处理、便于加云存档。
  但会带来：多一层抽象；各系统需实现序列化接口。

- **候选 C · run 状态归 run 系统，局外进度归局外系统，但都由统一存档层调度**：
  能提供：数据所有权清晰（谁的状态谁定义）+ 写入一致性（统一调度）。
  但会带来：需要明确两者的边界（什么算 run 内、什么算局外）。

- **候选 D · 全部状态集中在一个全局 store**：
  能提供：读写最简单。
  但会带来：数据所有权完全模糊，违背架构铁律；多人协作必冲突。

### 深度分析

判断标准是：**规范架构铁律「数据所有权唯一」如何与「持久化一致性」共存？**

规范原文：「每个状态只有一个系统有权修改」。注意是**修改权**，不是**存储权**。

候选 C 精确地区分了这两件事：
- **修改权**归各系统（run 系统改命数，局外系统改解锁）——符合铁律
- **存储权**归统一存档层——保证原子性与可迁移

这正是候选 B 的收益 + 候选 A 的清晰边界。

run 内 vs 局外的边界必须在架构阶段定死，否则下游会反复扯皮：

| 状态 | 归属 | run 结束时 |
|---|---|---|
| 命数 | run 内 | 清空，下次重置为满 |
| run 内能力集 | run 内 | 清空 |
| 当前关卡进度 | run 内 | 清空 |
| 已解锁能力池 | 局外 | 永久保留 |
| 章节解锁进度 | 局外 | 永久保留 |
| 历史最佳记录 | 局外 | 永久保留 |
| 关卡缓存 | 局外（技术层） | 保留 |

关键：**run 状态必须跨会话持久化**（上游要求：玩家可中断后次日继续）。这意味着 run 状态虽然是"临时的"，却必须写盘。

### 综合判断

**采用候选 C：数据修改权归各系统，存储权归统一的存档层。**

- **run 内状态**（命数、能力集、关卡进度）由 run 系统独占修改，但**必须跨会话持久化**以支持中断续玩。
- **局外状态**（能力池、章节进度、历史记录）由局外系统独占修改，永久保留。
- 存档层只负责收集快照、原子写入、版本迁移，**不做任何业务判断**。
- 边界表（上表）为契约，下游不得自行增删归属。

## 问题：呈现层要不要单列一个 GDD 系统？

状态：agent_proposal

### 广度分析

- **候选 A · 单列「信息呈现系统」**（如《刃种农庄》样例）：
  能提供：UI/可读性有明确责任方。
  但会带来：本游戏信息量极小（一屏网格 + 命数 + 能力图标），单列系统是形式主义。

- **候选 B · 不单列，呈现归执行文档**：
  能提供：GDD 聚焦规则与结构，避免文档膨胀。
  但会带来：可读性这一核心体验无人认领。

- **候选 C · 不单列系统，但在架构层声明「呈现契约」**：不设系统，但明确规定"呈现层只读状态、不做规则判断、不替玩家解题"，并在各系统的「不负责」清单中写明边界。
  能提供：守住"呈现与规则分离"的铁律，又不增加冗余系统。
  但会带来：呈现契约散落在各处，需要 GDD/README 集中索引。

- **候选 D · 单列，但归入 P1**：MVP 不写，等 UI 复杂后再补。
  能提供：MVP 精简。
  但会带来：可读性从第一天就是核心，等不起。

### 深度分析

判断标准是：**规范铁律「呈现与规则分离」的目的是什么？**

这条铁律的真实目的是防止两件事：
1. 呈现层偷偷做规则判断（导致规则不可测试、离线验证失效）
2. 呈现层替玩家解题（如自动高亮可行路径、自动排除无效方向）

这两条对本游戏**极其重要**：
- 第 1 条：如果渲染层做了"哪些格子可走"的判断，那么离线求解器的验证结论就与运行时不一致——**内容护城河直接崩塌**
- 第 2 条：本游戏的核心乐趣就是自己推演路径。任何"帮你排除无效方向"的辅助都是**在削掉核心玩法**

因此铁律必须守，但实现方式不必是单列一个系统——本游戏的信息呈现没有需要"决策"的内容，它只是**渲染 + 只读展示**。

候选 C 是正确的：把约束写成**契约**，在架构层集中声明一次，在各系统的「不负责」清单中落实。

特别需要契约锁死的一条：**禁止"自动排除无效方向"类的辅助**。
（即：不允许在 UI 上把"推不动的方向"置灰，或在滑动时阻止玩家输入。玩家必须能自己撞墙、自己发现走不通——这是学习过程的一部分。）

### 综合判断

**采用候选 C：不单列呈现系统，在架构层集中声明「呈现契约」，并在各系统的「不负责」清单中落实。**

呈现契约三条：
1. 呈现层**只读取状态**，不做任何规则判断。
2. 呈现层**不替玩家解题**——不自动高亮可行路径、不预测滑行结果、不排除无效方向。
3. 具体 UI 布局、美术规格、动效归执行文档与美术文档，GDD 不承载。

## 问题：MVP 的系统边界如何切，什么必须进 P0？

状态：agent_proposal

### 广度分析

- **候选 A · 三个系统（核心 + 关卡 + run）**：把能力并入 run，把局外并入关卡。
  能提供：文档最少，开发最快。
  但会带来：能力系统是差异化核心，并入 run 后无法独立演进；局外并入关卡会导致数据所有权混乱。

- **候选 B · 四个系统（核心 + 关卡 + run + 能力）**：去掉局外。
  能提供：验证核心假设（能力是否带来重玩价值）所需的最小集。
  但会带来：run 结束后什么都不留下，无法观测"成长感知"这一关键留存指标。

- **候选 C · 五个系统（核心 + 关卡 + run + 能力 + 局外）**：
  能提供：完整闭环，可上线验证留存与变现；每个系统职责单一。
  但会带来：MVP 工作量最大（但局外可取最小形态）。

- **候选 D · 六个系统（+ 呈现 / 社交）**：
  能提供：更细的分层。
  但会带来：呈现已决定不单列；社交依赖用户基数，MVP 无意义。

### 深度分析

判断标准是：**MVP 要验证的核心假设是什么，最少需要哪些系统？**

核心假设：**能力系统能否让滑行填充谜题产生 Roguelike 的重玩价值。**

验证它需要四系统（候选 B）。但候选 B 的致命问题是**测不出留存**：
run 结束 → 什么都没有 → 玩家没有"再来一局"的理由 → 无法区分"能力系统无效"和"没有长期目标"。

局外系统只需最小形态即可解决：
- 进度持久化（能力池解锁）
- 广告位预留（不做实际接入，留出位置）

这个最小形态的工作量很小，但让闭环可验证。

另外，能力系统必须独立成系统（不并入 run）的理由：
- 能力池、三选一规则、modifier 汇总逻辑是**独立的知识域**，与 run 的推进逻辑正交
- 独立后，能力系统可单独扩展（加能力不改 run）
- 规范目录映射要求系统拆分以架构为准，独立更利于后续维护

### 综合判断

**采用候选 C：五个 P0 系统——滑行核心、关卡、run、能力、局外。**
局外系统在 MVP 取最小形态：进度持久化 + 能力池解锁 + 广告位预留。每日挑战、排行榜、分享、皮肤一律 P1。
