## 三、本项目专属约定

### 3.1 关键设计取舍（贯穿全篇）

| 取舍 | 结论 | 理由 |
|------|------|------|
| **核心保留「全覆盖」** | 沿用 Longcat 的填满全部格子作为胜利条件 | 验证过的地基；可计算、可生成，这是内容护城河；视觉奇观最强 |
| **差异化压在元层，不改动核心** | 目标变体（收集+终点）、机制变体（冰块/传送门）一律降到 P1 | 保持核心谜题纯粹 + 架构分层干净（规则层与回收层分离） |
| **失败 = 少赚，不是毁档** | 困死只消耗一条命，能力保留，局外进度永久保留 | 规范 §8「保护机制对抗挫败」；微信小游戏留存刚需 |

### 3.2 与参考对象的数据接口

本 GDD 大量引用 Longcat 拆解的实证数据。**引用时只写结论，不复述推导**：

| 引用内容 | 来源 |
|---------|------|
| 单关步数基准（均值 13.02，区间 5–21） | `numbers/难度曲线实证数据.md` |
| 难度双旋钮（长度 vs 分支稀缺度） | `gameplay/核心循环与关卡结构.md` §4 |

| 微信小游戏硬约束 | `notes/对微信小游戏项目的启示.md` §1 |

### 3.3 本项目不写什么

遵循规范 §6 禁止项，并补充：

- 不写最终数值（命数、能力触发概率、关卡数量、广告频次）→ 归数值表
- 不写实现代码、不指定引擎 API → 归执行文档
- 不写 UI 布局与美术规格 → 归 UX / 美术文档
- **不写关卡的具体解法与布局** → 归关卡数据文件（远程 JSON）

## 四、一致性契约链（每次修订必跑）

引自规范 §7，本项目的检查要点：

1. **上游一致性**：是否违背 00 概念定稿 / 01 当前结论 / 02 目录映射？
2. **接口咬合**：上游「输出接口表」与下游「输入」是否同名同义？
3. **职责不重叠**：本系统「不负责」与相邻系统「负责」是否互斥？
4. **命名一致**：系统名、状态名、字段名在全篇是否同一写法？
5. **推迟兑现**：上游「本阶段不定」的每一项是否恰好在某下游被定义且只定义一次？
6. **闭环完整**：P0 最小闭环是否覆盖所有 P0 系统？验证标准是否可观测？
