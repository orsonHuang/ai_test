## 问题：三选一的 offer 如何生成——纯随机、加权，还是保证多样性？

状态：agent_proposal

### 广度分析

- **候选 A · 纯随机**：从已解锁能力池随机抽 3 个。
  能提供：实现最简单；完全不可预测，Roguelike 感最强。
  但会带来：可能连续抽到同类能力（三个都是撤销类），玩家觉得没选择；也可能一直抽不到关键能力。

- **候选 B · 加权随机**：按稀有度/强度加权。
  能提供：控制强度曲线（前期多给弱能力）。
  但会带来：需要维护权重表（这是数值工作）；且权重不解决"三个选项雷同"的问题。

- **候选 C · 分类保证 + 随机**：把能力池按 modifier 类型分组（撤销类 / 穿墙类 / 信息类 / 换关类），每次 offer 尽量覆盖不同类型。
  能提供：每次三选一都是**有意义的取舍**（我要更强的规则突破，还是要更多容错？）；避免选项雷同。
  但会带来：需要维护能力分类；池子小时可能凑不齐三类。

- **候选 D · 玩家可预览后续 offer（预先生成 run 的能力路线）**：
  能提供：可规划性。
  但会带来：削弱 Roguelike 的随机性；且本游戏核心决策已很重，不应再加长期规划负担。

### 深度分析

判断标准是：**三选一的价值来自哪里？**

三选一的设计目的是**每一次选择都让玩家感到"我的 run 变得不一样了"**。
如果三个选项是"撤销 1 次 / 撤销 2 次 / 撤销 3 次"，玩家的选择是**伪选择**——正确答案是显然的，没有取舍。

真正的取舍必须发生在**不同维度之间**：
- 规则突破（允许掉头、允许穿身）→ 让谜题变简单
- 容错（撤销、缩短尾巴）→ 让失误可挽回
- 信息（查看参考解）→ 让思考变轻松
- 换关 → 规避难题

这四类之间才有取舍。候选 C 通过"分类保证"强制每次 offer 跨类，直接制造了取舍。

候选 A 的问题正是它可能给出三个同类选项 → 伪选择。
候选 B 只解决强度，不解决维度。

另外要注意：**能力不是越强越好**。
"允许穿身"这类规则突破看似最强，但它会让谜题变得太简单，反而降低了通关的成就感。
而"撤销 1 次"看似弱，却能精确救回一次失误。
这种"没有绝对最优"的平衡，正是分类保证带来的副产品。

### 综合判断

**采用候选 C：能力池按 modifier 类型分组（规则突破 / 容错 / 信息 / 换关），三选一的 offer 尽量跨类抽取，保证每次选择是维度间的取舍而非强度比较。**
能力池不足三类时降级为随机（不阻塞流程）。

## 问题：能力是否可叠加、可升级？

状态：agent_proposal

### 广度分析

- **候选 A · 不可叠加**：每个能力只能获得一次，池子里拿走就没了。
  能提供：能力集清晰，modifier 汇总简单。
  但会带来：重复抽到已拥有的能力时要重抽；run 后期无能力可选。

- **候选 B · 可叠加（次数累加）**：同类能力可重复获得，次数叠加（撤销 1 次 + 撤销 1 次 = 撤销 2 次）。
  能提供：能力永不枯竭；后期能形成"撤销 5 次"这样的极端 build，有爽感。
  但会带来：次数累加本质是**数值成长**——与"能力只改规则不改数值"的概念定稿冲突；且会破坏谜题难度（撤销 5 次等于随便试）。

- **候选 C · 可升级（同类能力合并为高阶版本）**：获得重复能力时升级为质变版本（如"撤销 1 次" → "撤销不限次数但每关限一次"）。
  能提供：保留叠加的成长感，但每次升级是**规则变化**而非数值堆砌。
  但会带来：需要为每个能力设计升级形态，设计工作量大。

- **候选 D · 不可叠加，但获得重复能力时转化为其他资源**：
  能提供：解决重复问题。
  但会带来：引入货币/转化系统，与"无数值系统"冲突。

### 深度分析

判断标准是：**"能力只改规则不改数值"这条概念定稿，边界在哪？**

这条约束的真实目的是防止两件事：
1. 引入需要平衡的数值系统（工作量黑洞）
2. 能力通过数值膨胀让谜题失去挑战

候选 B 两条都犯：撤销 5 次 = 玩家可以随便试错 = 谜题退化。

候选 A 最符合约束，但有个实际问题：run 后期能力池抽空。
不过这个问题可以量化：MVP 能力池 12–15 个，一次 run 十几关 → 需要十几到二十几个能力。
**池子确实不够**。

候选 C 是最优解：升级是**质变**而非量变。
例如：
- 「撤销 1 次」→「撤销 1 次，且撤销不消耗次数上限」（规则变化）
- 「允许掉头」→「允许掉头，且掉头后可继续滑行」（规则变化）
- 「查看参考解 1 步」→「查看参考解全部剩余步」（规则变化）

每次升级改变的是**规则的形状**，不是数字。这既保留了成长感，又不违反约束。

但它要求每个能力都设计升级形态——MVP 阶段成本高。
折中：**MVP 只给核心能力（3–5 个）设计升级形态，其余能力采用候选 A（不叠加）**。

### 综合判断

**采用 C 为主 + A 兜底：**
- 默认：能力不可叠加，每个能力在 run 内只能持有一次
- 核心能力（MVP 3–5 个）设计**质变型升级形态**，重复获得时升级
- 升级必须改变规则的形状，不得是次数累加
- **禁止**纯次数叠加（候选 B）与货币转化（候选 D）

具体哪些能力有升级形态归数值表/能力表，本阶段不定。

## 问题：如何保证 modifier 的放宽性不出错？

状态：agent_proposal

### 广度分析

- **候选 A · 人工评审**：每个能力上线前人工论证放宽性。
  能提供：无工程成本。
  但会带来：人会犯错；能力池扩大后不可持续；无法覆盖能力组合的情况。

- **候选 B · 运行时断言**：每次注入 modifier 时检查合法移动集合是否单调不减。
  能提供：实时发现问题。
  但会带来：需要计算合法移动集合（额外开销）；且运行时才发现已经晚了（关卡已经进行中）。

- **候选 C · 离线穷举校验**：对「全部能力 × 全部关卡 × 若干代表性局面」做离线组合验证，确认参考解在任意组合下仍成立。
  能提供：**数学级保证**；问题在上线前暴露；可自动化、可持续。
  但会带来：组合空间大（2^N 种能力组合），需采样或剪枝。

- **候选 D · 类型系统保证**：用 TypeScript 类型约束 modifier 只能是放宽型。
  能提供：编译期保证。
  但会带来：类型系统无法表达"放宽"这种语义约束（它只能管类型，管不了行为）。

### 深度分析

判断标准是：**这个保证的失效代价有多大？**

如果某个 modifier 意外收紧了约束，后果是：
> 某关卡在某能力组合下变得无解 → 玩家卡死 → 消耗所有命 → run 失败 → **玩家会认为是游戏 bug，而不是自己菜**

这直接摧毁两样东西：
1. 玩家信任（"这游戏有关卡根本过不去"）
2. 内容护城河（"关卡 100% 可解"的承诺失效）

这是本项目**最严重的失效模式**，值得用最重的手段防。

候选 C 是唯一能在**上线前**给出保证的方案。关键是它的组合爆炸问题怎么解：

关键洞察：**放宽性是可组合的**。
如果 modifier A 是放宽的，B 是放宽的，那么 A+B 必然也是放宽的（两次超集运算的复合仍是超集）。

因此**不需要穷举 2^N 种组合**——只需**逐个验证每个 modifier 单独是放宽的**，组合的放宽性由数学传递性保证。

这让候选 C 的成本从指数降到线性：**N 个能力，只需 N 次验证**。

具体验证方式：对每个 modifier，在离线跑一批代表性局面，检查应用前后的合法移动集合是否满足包含关系。

候选 B 作为运行时的兜底断言（开发期开启，上线关闭）也可保留，但不是主要手段。

### 综合判断

**采用候选 C（逐个验证，非组合穷举）+ 候选 B 作为开发期兜底断言。**

- **验证方式**：离线对每个 modifier 单独验证放宽性——在代表性局面集合上，确认「应用后的合法移动集合 ⊇ 应用前的合法移动集合」。
- **数学依据**：放宽性可复合传递（超集运算的复合仍是超集），故 N 个能力只需 N 次验证，无需 2^N 次组合穷举。
- **门禁**：验证不通过的 modifier 不得进入能力池。此校验纳入离线工具链，与关卡验证同一条流水线。
- 开发期在运行时保留断言（可关闭），用于捕获离线未覆盖的边界情况。
