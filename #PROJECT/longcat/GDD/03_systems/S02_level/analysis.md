## 问题：难度分级用什么指标——步数、解的数量，还是首步容错率？

状态：agent_proposal

### 广度分析

- **候选 A · 以最短解步数为难度指标**：
  能提供：计算最简单，直观易懂。
  但会带来：**已被实证证伪**——Longcat 50 关中 37% 的关卡比前一关更短（第 14 关 14 步 → 第 15 关 8 步），步数与难度弱相关。用它分级会造出"又长又无聊"的关卡。

- **候选 B · 以解的数量为难度指标**（解越少越难）：
  能提供：直击"分支稀缺度"——这才是真正的难度来源；可由求解器穷举得到。
  但会带来：需要穷举全部解，对稍大网格开销大；且"解的数量"是全局指标，不反映玩家在前几步的真实体验。

- **候选 C · 以首步容错率为难度指标**（第一步四个方向中能通关的比例）：
  能提供：直接对应玩家的第一印象与重开次数；计算便宜（只需对 4 个首步各跑一次求解）。
  但会带来：只看第一步，忽略中后段的陷阱。

- **候选 D · 组合指标（解的数量 + 首步容错率 + 死腔触发率）加权**：
  能提供：多维度刻画难度，可分别调节"整体稀缺度"与"开局挫败感"。
  但会带来：权重需要调参；指标越多关卡筛选越慢。

### 深度分析

判断标准是：**难度指标必须能同时服务两个目的——给玩家排序关卡，以及给生成器筛选关卡。**

拆解实证（`#Game-TearDown/Longcat/numbers/难度曲线实证数据.md`）给出三条硬事实：
1. 步数与难度弱相关（37% 回落率）
2. 中后期靠结构复杂度而非长度（41–50 段均值 16.1 < 31–40 段 16.5）
3. 存在刻意的回落调剂关（第 15/40/47 关）

候选 A 与事实 1、2 直接冲突，排除。

候选 B、C 各有盲区，但它们**互补得近乎完美**：
- 解的数量 = 全局稀缺度（这关有多刁）
- 首步容错率 = 开局挫败感（玩家要重开几次）

两者组合已经覆盖了玩家体验的两端。**死腔触发率**可以由前两者间接反映，单独加入性价比不高。

因此采用候选 D 的**精简版**：解的数量 + 首步容错率两个指标，不加第三个。

另外必须保留一条来自拆解的编排经验：**难度序列需要刻意的回落**。生成器产出关卡后，编排算法要按"高压关后插调剂关"的模式排列，而不是单调升序。

### 综合判断

**采用候选 D 的精简版：难度 = 解的数量（主）+ 首步容错率（辅）的双指标加权。**
不使用步数作为难度指标（它只用作关卡的展示信息与"最短步数"挑战目标）。

**编排硬约束**：关卡序列不得单调升序，必须按拆解实证的比例（约 1/3）插入回落调剂关。

## 问题：参考解要不要内嵌进关卡 JSON？

状态：agent_proposal

### 广度分析

- **候选 A · 不内嵌，提示功能靠运行时求解**：
  能提供：关卡数据最小。
  但会带来：需要运行时求解器（架构已否决）；小游戏端算力不足，穷举会卡顿。

- **候选 B · 内嵌一条参考解**：
  能提供：提示功能零运行时开销；可用于"是否还有解"的偏离检测；数据量极小（每关十几个方向，几十字节）。
  但会带来：提示只能给标准答案，不能给"基于当前局面的建议"。

- **候选 C · 内嵌全部解**：
  能提供：最灵活的提示。
  但会带来：数据量爆炸（某些关卡有上百个解）；泄露谜题。

- **候选 D · 内嵌一条参考解 + 一个"死局判定标记"**：
  能提供：在 B 的基础上，能快速判断玩家是否已进入死局。
  但会带来：死局判定需要比对玩家路径与解空间，仅靠一条参考解无法完成。

### 深度分析

判断标准是：**提示功能到底需要什么？**

架构决策已定：运行时不实现求解器。因此提示只能来自预存数据（候选 B）。

关键问题是候选 B 的短板——"不能给基于当前局面的建议"——**是不是真的问题？**

回到玩法本质：**每一步都是不可逆的**。玩家卡住时，往往是开局路线就错了，此时"基于当前局面的下一步"很可能根本不存在（已进入死局）。
所以真正有用的提示是两种：
1. **给标准路线的下一步**——引导玩家理解这关的解题思路
2. **告诉玩家"你已经进死局了，重开吧"**——止损，比让玩家继续挣扎体验好得多

第 1 点候选 B 直接满足。
第 2 点不需要"死局标记"——**玩家路径一旦偏离参考解，且当前已困死，就已经触发 STUCK 判定了**。
真正的痛点是"还没困死但已经无解"——这个确实需要求解能力，但**它可以通过"偏离参考解即提示风险"来近似**：玩家路径偏离参考解时，给出温和提示"当前路线可能走不通"。

这个方案不完美但足够好，且零运行时开销。完美方案（运行时求解）已被架构否决。

### 综合判断

**采用候选 B：关卡 JSON 内嵌一条参考解（方向序列）。**
提示功能直接读取参考解的下一步；"路线可能走不通"的提示通过**玩家路径与参考解的偏离检测**近似实现，不做运行时穷举。
**不内嵌全解，不做死局判定标记。**

## 问题：关卡数据格式与内置/远程的切分点在哪？

状态：agent_proposal

### 广度分析

- **候选 A · JSON 字符串网格 + 元数据，前 20–30 关内置**：
  能提供：格式紧凑易压缩、易 diff、易远程传输；内置部分保证首屏零网络依赖。
  但会带来：需维护两套加载路径（内置 resource vs 远程 HTTP）。

- **候选 B · 全部远程，首页关卡单独预热**：
  能提供：单一加载路径。
  但会带来：弱网/离线时首关都进不去，启动即流失。

- **候选 C · 全部内置，用分包承载**：
  能提供：单一加载路径 + 离线可用。
  但会带来：关卡量受分包上限约束；更新关卡仍需提审。

- **候选 D · 内置关卡以代码生成（程序化种子）**：
  能提供：包体极小。
  但会带来：内置关卡无法手工精调教学；且程序化生成的不稳定性会影响第一印象。

### 深度分析

判断标准是：**第一印象与内容产能，哪个更不能妥协？**

两者都不能。但它们的冲突是可调和的：
- **教学与首章（前 20–30 关）**：质量要求最高（决定留存），数量需求最低 → **手工设计 + 内置**
- **后续内容**：数量需求最高，质量要求可由求解器保证 → **程序生成 + 远程**

这正好对应候选 A。它的唯一代价是"两套加载路径"，但这个代价很小——加载器可以统一成一个接口，内部按 ID 范围分发到内置或远程，对上层完全透明。

格式选择：网格用**字符串**（如 `"####...#..#"`）而非二维数组。理由：
- 体积小（500 关 JSON 压缩后差异明显）
- 易 diff、易人工检视、易在关卡编辑器里编辑
- 解析成本可忽略

### 综合判断

**采用候选 A：网格用字符串编码的 JSON 格式；前 20–30 关（手工设计的教学与首章）内置，其余全部远程按章节懒加载 + 本地缓存。**

- 加载器对上层暴露统一接口（`requestLevel(id)`），内部按 ID 分发，上层不感知内置/远程差异。
- 远程失败降级：优先本地缓存 → 回退内置关卡池（策略细节归执行文档）。
- 具体字段与编码规范见 `design.md` 状态与字段表。
