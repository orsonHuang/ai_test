## 问题：难度分级用什么指标——步数、解的数量，还是首步容错率？

状态：user_confirmed

### 广度分析

- **候选 A · 以最短解步数为难度指标**：
  能提供：计算最简单，直观易懂。
  但会带来：**已被实证证伪**——Longcat 50 关中 37% 的关卡比前一关更短，步数与难度弱相关。用它分级会造出"又长又无聊"的关卡。

- **候选 B · 以解的数量为难度指标**（解越少越难）：
  能提供：直击"分支稀缺度"——这才是真正的难度来源；可由求解器穷举得到。
  但会带来：需要穷举全部解，对稍大网格开销大；且"解的数量"是全局指标，不反映玩家在前几步的真实体验。

- **候选 C · 以首步容错率为难度指标**（第一步四个方向中能通关的比例）：
  能提供：直接对应玩家的第一印象与重开次数；计算便宜（只需对 4 个首步各跑一次求解）。
  但会带来：只看第一步，忽略中后段的陷阱。

- **候选 D · 组合指标（解的数量 + 首步容错率）加权**：
  能提供：多维度刻画难度，可分别调节"整体稀缺度"与"开局挫败感"。
  但会带来：权重需要调参；指标越多关卡筛选越慢。

### 深度分析

判断标准是：**难度指标必须能同时服务两个目的——给玩家排序关卡，以及给生成器筛选关卡。**

拆解实证给出三条硬事实：
1. 步数与难度弱相关（37% 回落率）
2. 中后期靠结构复杂度而非长度
3. 存在刻意的回落调剂关

候选 A 与事实 1 直接冲突，排除。

候选 B、C 各有盲区，但它们**互补得近乎完美**：
- 解的数量 = 全局稀缺度（这关有多刁）
- 首步容错率 = 开局挫败感（玩家要重开几次）

两者组合已经覆盖了玩家体验的两端。

### 综合判断

**采用候选 D：难度 = 解的数量（主）+ 首步容错率（辅）的双指标加权。**
不使用步数作为难度指标（它只用作关卡的展示信息）。

## 问题：参考解要不要内嵌进关卡 JSON？

状态：user_confirmed

### 广度分析

- **候选 A · 不内嵌，提示功能靠运行时求解**：
  能提供：关卡数据最小。
  但会带来：需要运行时求解器（架构已否决）；小游戏端算力不足，穷举会卡顿。

- **候选 B · 内嵌一条参考解**：
  能提供：提示功能零运行时开销；可用于"是否还有解"的偏离检测；数据量极小（每关十几个方向，几十字节）。
  但会带来：提示只能给标准答案，不能给"基于当前局面的建议"。

- **候选 C · 内嵌全部解**：
  能提供：最灵活的提示。
  但会带来：数据量爆炸（某些关卡有上百个解）；泄露谜题。

- **候选 D · 内嵌一条参考解 + 一个"死局判定标记"**：
  能提供：在 B 的基础上，能快速判断玩家是否已进入死局。
  但会带来：死局判定需要比对玩家路径与解空间，仅靠一条参考解无法完成。

### 深度分析

判断标准是：**提示功能到底需要什么？**

架构决策已定：运行时不实现求解器。因此提示只能来自预存数据（候选 B）。

关键问题是候选 B 的短板——"不能给基于当前局面的建议"——**是不是真的问题？**

回到玩法本质：**每一步都是不可逆的**。玩家卡住时，往往是开局路线就错了，此时"基于当前局面的下一步"很可能根本不存在（已进入死局）。
所以真正有用的提示是两种：
1. **给标准路线的下一步**——引导玩家理解这关的解题思路
2. **告诉玩家"你已经进死局了，重开吧"**——止损，比让玩家继续挣扎体验好得多

第 1 点候选 B 直接满足。
第 2 点不需要"死局标记"——**玩家路径一旦偏离参考解，且当前已困死，就已经触发 STUCK 判定了**。

### 综合判断

**采用候选 B：关卡 JSON 内嵌一条参考解（方向序列）。**
提示功能直接读取参考解的下一步；"路线可能走不通"的提示通过**玩家路径与参考解的偏离检测**近似实现，不做运行时穷举。
**不内嵌全解，不做死局判定标记。**

## 问题：网格尺寸如何工程化——静态配置、动态计算，还是生成器参数？

状态：user_confirmed

### 广度分析

- **候选 A · 静态配置表**：在关卡数据或配置文件中硬编码每关的网格尺寸。
  能提供：最直观，策划可直接调整节奏。
  但会带来：关卡量大时维护成本高；新增关卡需要手动指定尺寸。

- **候选 B · 动态计算（按序号取模）**：根据关卡序号动态计算网格尺寸（如 `sizeIndex = levelIndex % 10`，映射到小/中/大）。
  能提供：零配置，关卡生成器自动遵循节奏；新增关卡无需额外处理。
  但会带来：节奏固定，无法灵活调整。

- **候选 C · 生成器参数化**：生成器接受"节奏模板"参数，生成关卡时按模板分配尺寸。
  能提供：节奏可配置，生成器自动遵循；模板可热更新。
  但会带来：需要设计模板格式与解析逻辑。

- **候选 D · 混合（动态计算 + 模板覆盖）**：默认按序号取模，但支持配置模板覆盖默认节奏。
  能提供：默认零配置，特殊需求可覆盖。
  但会带来：两套逻辑并存，可能产生混乱。

### 深度分析

判断标准是：**网格循环的本质是什么？**

网格循环是**节奏设计**，不是关卡内容。它的目的是让玩家体验"热身→深入→挑战→重置"的节拍。

候选 B（动态计算）最简洁：
- 关卡序号确定 → 网格尺寸确定
- 生成器只需知道当前关卡的序号，自动分配尺寸
- 无需额外配置，无需维护映射表

节奏定义（每 10 关一个循环）：
- 关卡 0, 1 → 小网格（4×5 ~ 5×6）
- 关卡 2, 3, 4 → 中网格（6×7 ~ 7×8）
- 关卡 5, 6, 7, 8, 9 → 大网格（7×8 ~ 8×10）

### 综合判断

**采用候选 B：动态计算，按关卡序号取模确定网格尺寸。**

节奏公式：
```
sizeIndex = levelIndex % 10
if sizeIndex < 2: small (4×5 ~ 5×6)
elif sizeIndex < 5: medium (6×7 ~ 7×8)
else: large (7×8 ~ 8×10)
```

- 关卡生成器自动遵循此节奏。
- 无需额外配置，新增关卡无需手动指定尺寸。
- 若未来需要调整节奏，修改公式即可。

## 问题：关卡数据格式与内置/远程的切分点在哪？

状态：user_confirmed

### 广度分析

- **候选 A · JSON 字符串网格 + 元数据，前 20–30 关内置**：
  能提供：格式紧凑易压缩、易 diff、易远程传输；内置部分保证首屏零网络依赖。
  但会带来：需维护两套加载路径（内置 resource vs 远程 HTTP）。

- **候选 B · 全部远程，首页关卡单独预热**：
  能提供：单一加载路径。
  但会带来：弱网/离线时首关都进不去，启动即流失。

- **候选 C · 全部内置，用分包承载**：
  能提供：单一加载路径 + 离线可用。
  但会带来：关卡量受分包上限约束；更新关卡仍需提审。

- **候选 D · 内置关卡以代码生成（程序化种子）**：
  能提供：包体极小。
  但会带来：内置关卡无法手工精调教学；且程序化生成的不稳定性会影响第一印象。

### 深度分析

判断标准是：**第一印象与内容产能，哪个更不能妥协？**

两者都不能。但它们的冲突是可调和的：
- **教学与首段（前 20–30 关）**：质量要求最高（决定留存），数量需求最低 → **手工设计 + 内置**
- **后续内容**：数量需求最高，质量要求可由求解器保证 → **程序生成 + 远程**

这正好对应候选 A。它的唯一代价是"两套加载路径"，但这个代价很小——加载器可以统一成一个接口，内部按 ID 范围分发到内置或远程，对上层完全透明。

格式选择：网格用**字符串**（如 `"####...#..#"`）而非二维数组。理由：
- 体积小（500 关 JSON 压缩后差异明显）
- 易 diff、易人工检视、易在关卡编辑器里编辑
- 解析成本可忽略

### 综合判断

**采用候选 A：网格用字符串编码的 JSON 格式；前 20–30 关（手工设计的教学与首段）内置，其余全部远程按批次懒加载 + 本地缓存。**

- 加载器对上层暴露统一接口（`requestLevel(id)`），内部按 ID 分发，上层不感知内置/远程差异。
- 远程失败降级：优先本地缓存 → 回退内置关卡池（策略细节归执行文档）。
- 具体字段与编码规范见 `design.md` 状态与字段表。

## 问题：进度持久化如何设计？

状态：user_confirmed

### 广度分析

- **候选 A · 关卡系统自行持久化**：关卡系统存储当前关卡序号、每关通关记录。
  能提供：职责清晰，关卡相关数据集中管理。
  但会带来：若未来加入成就系统，成就数据无处安放。

- **候选 B · 统一存档层**：一个持久化服务收集各系统的状态快照，统一写入。
  能提供：原子写入、版本迁移集中处理、便于加云存档。
  但会带来：多一层抽象；各系统需实现序列化接口。

- **候选 C · 关卡进度归关卡系统，成就归成就系统，但都由统一存档层调度**：
  能提供：数据所有权清晰 + 写入一致性。
  但会带来：MVP 阶段成就系统未实现，存档层可能过度设计。

- **候选 D · 全部状态集中在一个全局 store**：
  能提供：读写最简单。
  但会带来：数据所有权完全模糊，违背架构铁律。

### 深度分析

判断标准是：**MVP 阶段需要多复杂的持久化方案？**

MVP 只有两个系统：滑行核心 + 关卡。需要持久化的状态：
- 当前关卡序号（进度）
- 每关通关记录（用于成就/收集的基础）

这些数据量小、结构简单，关卡系统可以独立管理。

但若未来加入成就系统、社交系统，数据所有权会分散，需要统一存档层保证一致性。

**MVP 阶段采用候选 A（关卡系统自行持久化），但预留存档层接口**，未来扩展时平滑迁移到候选 C。

### 综合判断

**采用候选 A（MVP）：关卡进度与通关记录由关卡系统自行持久化。**

- MVP 只需存储：当前关卡序号、每关通关记录。
- 预留存档层接口，未来成就/社交系统接入时迁移到统一存档层。
- 存储方式：微信小游戏本地存储（`wx.setStorage`），未来可扩展云存档。
