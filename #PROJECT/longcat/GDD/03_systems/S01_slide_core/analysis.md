## 问题：初始身体长度定为 1 还是 2？

状态：agent_proposal

### 广度分析

- **候选 A · 初始长度 1（只有猫头）**：
  能提供：教学最干净——玩家从一个点开始，第一次滑行必定成功（除非四面被围）；关卡数据无需定义初始朝向。
  但会带来：首次滑行前"尾巴"概念不存在，撞身体规则要在滑行后才生效。

- **候选 B · 初始长度 2（头 + 尾）**：
  能提供：从第一步起"身体即障碍"的规则就完整成立；视觉上一开始就是"一只猫"而非"一个点"。
  但会带来：关卡数据必须额外定义初始朝向；初始朝向错误会让关卡直接无解，增加生成器约束与出错面。

- **候选 C · 初始长度随难度变化（前期 1、后期 2）**：
  能提供：难度调节的新维度。
  但会带来：规则不一致会破坏玩家的心智模型；求解器要为两种初始状态分别验证。

- **候选 D · 初始长度 1，但起点占两格（头 + 备用格）**：
  能提供：折中方案。
  但会带来：概念复杂，玩家难以理解"备用格"是什么。

### 深度分析

判断标准是：**哪条规则能让"规则集最小"且"求解器验证最简单"？**

候选 B 引入的"初始朝向"是一个隐藏成本：它让关卡数据多一个字段，且这个字段出错会直接导致关卡无解。而它换来的收益（第一步起规则完整）其实**可以被另一条规则覆盖**——见下一题的"无效移动"规则。

候选 A 的关键优势：**第一次滑行必定有效**（长度 1 时无身体阻挡，除非正对墙）。这让第 1 关的教学极其干净：玩家怎么滑都有反应，立刻理解"滑到撞墙为止"。

而且候选 A 下，"掉头"这个场景要滑行至少一次后才可能出现——那时玩家已经理解了滑行规则，再遇到"掉头无效"是自然延伸，不是额外规则。

### 综合判断

**采用候选 A：初始身体长度为 1（只有猫头，位于关卡起点）。**
关卡数据不需要初始朝向字段。尾巴/身体障碍规则在滑行后自然生效。

## 问题：撞到自己的身体，是「停下」还是「判负」？

状态：agent_proposal

### 广度分析

- **候选 A · 停下（身体即墙）**：滑行到身体前一格停住，本步结束。
  能提供：玩家可以把自己的身体当墙用——这是深度的来源（用身体制造新的阻挡点）；失败只发生在"四向都动不了"。
  但会带来：无。

- **候选 B · 判负（撞到即死）**：撞到自己身体直接困死。
  能提供：紧张感更高。
  但会带来：玩家会倾向于保守走位；且"撞墙停下、撞身体却死"两条规则不一致，心智负担重。

- **候选 C · 撞到身体停下，但立即判定是否还有解，无解则判负**：
  能提供：减少玩家在死局里空转的时间。
  但会带来：等于让系统替玩家判断"你输了"，剥夺了玩家自己发现死局的思考过程；且需要运行时求解器。

- **候选 D · 尾巴可穿过，身体不可穿过**：
  能提供：更宽松的规则。
  但会带来：尾巴与身体难以区分，玩家困惑；求解器复杂度上升。

### 深度分析

判断标准是：**身体在本游戏中承担什么角色？**

拆解研究表明，Longcat 的身体有双重身份：**既是障碍，也是进度**。
候选 A 让这个双重身份成立——身体是墙（障碍），但每多一节身体就意味着离通关更近（进度）。玩家会主动利用身体制造转角，这是策略深度的主要来源。

候选 B 摧毁了这一设计：身体变成纯惩罚源，玩家会规避它，而不是利用它。

候选 C 的致命问题是**它让系统替玩家解题**。本游戏的核心乐趣就是自己推演路径、自己发现死局。如果系统在玩家走进死局时立刻宣告失败，等于剥夺了思考过程。而且它需要运行时求解器，与架构决策（运行时不实现求解器）冲突。

### 综合判断

**采用候选 A：身体（含尾巴）视同墙，滑行到它前面停下。**
失败只有一种：四向均无法产生有效移动且未填满。不提前宣告死局，不替玩家判断。

## 问题：无效移动（滑行 0 格）如何处理？

状态：agent_proposal

### 广度分析

- **候选 A · 输入作废，不消耗回合，不改变任何状态**：
  能提供：零成本试探——玩家可以在想不清楚时用手指去试；且"掉头"这一场景被同一条规则自然覆盖。
  但会带来：玩家可能无脑四向乱试（但这不构成问题，因为试不出信息）。

- **候选 B · 消耗一步，但状态不变**：
  能提供：让"乱试"有代价。
  但会带来：本游戏无步数限制，消耗一步毫无意义；且会惩罚正常玩家的误操作。

- **候选 C · 输入作废，但给出提示反馈（如震动/抖动）**：
  能提供：让玩家明确知道"这个方向走不了"。
  但会带来：这属于呈现层的辅助反馈，需注意不要演变成"自动排除无效方向"（见架构呈现契约第 3 条）。

- **候选 D · 额外设立「禁止掉头」规则单独处理反向输入**：
  能提供：规则表述更直白。
  但会带来：增加一条独立规则；且与"撞身体停下"逻辑重复。

### 深度分析

判断标准是：**能否用最少的规则覆盖最多的场景？**

关键洞察：**候选 A 一条规则同时覆盖四个场景**：
1. 正对边界 → 路径 0 格 → 无效
2. 正对墙 → 路径 0 格 → 无效
3. 正对身体 → 路径 0 格 → 无效
4. **反向掉头**（长度 ≥2 时，head 相邻格是自己第二节身体）→ 路径 0 格 → 无效

第 4 点尤其优雅：**不需要单独的"禁止掉头"规则**，它是"身体即墙"的自然推论。这印证了 Longcat 官方解法序列中"从不出现相邻反向"的现象（见 `#Game-TearDown/Longcat/gameplay/核心机制拆解.md` B2）。

关于候选 C 的反馈：可以给**轻微的反馈**（如猫头撞墙的动画），但**绝不能把方向置灰或阻止输入**。玩家必须能自己撞墙——这是学习过程。

### 综合判断

**采用候选 A（+ 候选 C 的轻反馈）：滑行路径为 0 格时，输入作废，不消耗回合，不改变任何状态。**
不设立独立的「禁止掉头」规则——它是「身体即墙」的自然推论。
反馈限制：可给轻微撞击反馈，**禁止把无效方向置灰或阻止输入**（架构呈现契约第 3 条）。

## 问题：modifier 参数集包含哪些，如何保证「放宽约束」？

状态：agent_proposal

### 广度分析

- **候选 A · 最小参数集（3 个）**：撤销次数、允许掉头、允许穿身。
  能提供：实现最简单，校验最容易。
  但会带来：MVP 的 12–15 个能力会高度雷同（只能靠数值区分次数）。

- **候选 B · 中等参数集（5–7 个）**：撤销次数、允许掉头、允许穿身、撞碎墙、缩短尾巴、查看参考解、换关。
  能提供：12–15 个能力有足够的区分度，且每个都是明确的规则变化。
  但会带来：每个参数都要单独校验"放宽性"。

- **候选 C · 大参数集（10+）**：加入滑行距离修改、格子类型转换等。
  能提供：能力设计空间大。
  但会带来：部分参数无法证明放宽性（如"滑行距离 +1"可能让玩家错过转角，反而更难）；校验成本指数上升。

- **候选 D · 开放参数（任意数值修改）**：
  能提供：最大自由度。
  但会带来：直接违背"能力只改规则不改数值"的概念定稿；且无法保证放宽性。

### 深度分析

判断标准是：**什么是「放宽约束型」modifier 的严格定义？**

**定义：一个 modifier 是放宽约束型，当且仅当——在任何局面下，应用它之后的合法移动集合 ⊇ 应用之前的合法移动集合。**

换句话说：**能力只能让玩家"多出选择"，永远不能"减少选择"。**

这个定义有一个极强的推论：
> 若关卡在无能力时可解，则在任意能力组合下也可解。
> （因为无能力时的解法序列，每一步在应用 modifier 后仍然合法）

这正是上游要求的性质。逐条检验候选 B 的参数：

| modifier | 是否放宽 | 理由 |
|---|---|---|
| 撤销 N 次 | ✅ | 新增"回退"选项，不减少任何原有选项 |
| 允许掉头 | ✅ | 新增反向移动选项 |
| 允许穿身 | ✅ | 新增穿过身体的选项 |
| 撞碎墙 N 次 | ✅ | 新增破坏墙的选项 |
| 缩短尾巴 N 格 | ✅ | 移除已填格 = 移除障碍，严格增加可走空间 |
| 查看参考解 | ✅ | 纯信息，不改变移动集合 |
| 换一张同难度关 | ✅ | 不改变本关的移动集合（是换关，不是改规则） |
| ~~滑行距离 +1~~ | ❌ | 可能让玩家错过转角，**收紧**约束 |
| ~~禁止某方向~~ | ❌ | 明显收紧 |

候选 C 里的"滑行距离修改"类参数被证伪，这正是需要较小参数集的理由。

### 综合判断

**采用候选 B：modifier 参数集限定为 7 个放宽型参数**——撤销次数、允许掉头、允许穿身、撞碎墙次数、缩短尾巴格数、查看参考解次数、换关次数。

**硬约束（写入 S04）**：
- 「放宽约束」的严格定义 = 应用后合法移动集合 ⊇ 应用前。
- 任何新增 modifier 必须通过此定义的检验，否则不纳入。
- modifier 只能由 S04 汇总产出一个参数对象，S01 只接收参数、不感知能力概念。

## 问题：离线验证与运行时如何保证行为一致？

状态：agent_proposal

### 广度分析

- **候选 A · 各写一份**：离线工具用 Python/JS 独立实现，运行时用 TypeScript。
  能提供：各自可用最顺手的语言。
  但会带来：**两份实现必然分叉**，离线验证"有解"的关卡在运行时可能行为不同——内容护城河直接失效。

- **候选 B · 共用同一份 TypeScript 规则代码**：`core/` 层不依赖 Cocos，离线工具与运行时都 import 它。
  能提供：**行为一致的数学保证**；规则改动一次生效两处；`core/` 可跑 node 单测。
  但会带来：离线工具也必须用 TypeScript/node 技术栈（这是优点不是代价）。

- **候选 C · 运行时调用离线服务（云端求解）**：
  能提供：只需一份实现。
  但会带来：需要后端；运行时网络依赖；且每日挑战等场景不可用。

- **候选 D · 共用代码 + 定期回归比对**：
  能提供：双保险。
  但会带来：若已共用同一份代码，回归比对是冗余的。

### 深度分析

判断标准是：**内容护城河的前提是什么？**

本项目的护城河是「关卡可批量生成且 100% 可验证」。这个前提有一个隐藏依赖：
**验证器的行为必须与实际游玩的行为完全一致。**

如果离线求解器说"这关有解，解法是 ↑→↓←"，但运行时因为实现差异导致某一步滑行距离不同，那么：
- 提示功能会给错误提示
- 难度评分失真
- 最坏情况下出现"验证有解但实际无解"的关卡 → 玩家卡死 → 信任崩塌

候选 B 是唯一能从**结构上**（而非流程上）杜绝这个问题的方案：同一份代码，不可能分叉。

这也是架构铁律「逻辑与引擎解耦」（`#PROJECT/longcat/README.md` 工作规则 3）的直接收益——`core/` 不依赖 Cocos，所以离线 node 脚本能直接 import。

### 综合判断

**采用候选 B：`core/` 层为不依赖 Cocos 的纯 TypeScript，离线生成器/求解器与运行时游戏共用同一份规则代码。**

工程约束：
- `core/` 不得 import 任何 Cocos 模块、不得访问任何引擎 API、不得依赖运行时环境。
- `core/` 必须可用 `node` 直接跑单测。
- 任何规则改动只需改 `core/` 一处，离线与运行时同步生效。
