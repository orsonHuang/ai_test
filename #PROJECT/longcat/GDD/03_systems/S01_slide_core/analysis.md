## 问题：初始猫咪状态如何设定？

状态：user_confirmed

### 广度分析

- **候选 A · 起点只有猫（占一格）**：
  能提供：教学最干净——玩家从一个点开始，第一次划线必定成功（除非四面被围）；关卡数据无需定义初始朝向。
  但会带来：首次划线前"蒲公英"概念不存在，撞蒲公英规则要在划线后才生效。

- **候选 B · 起点猫 + 一节蒲公英（占两格）**：
  能提供：从第一步起"蒲公英即障碍"的规则就完整成立；视觉上一开始就是"一只猫站在草地上"。
  但会带来：关卡数据必须额外定义初始朝向；初始朝向错误会让关卡直接无解，增加生成器约束与出错面。

- **候选 C · 初始长度随难度变化（前期 1、后期 2）**：
  能提供：难度调节的新维度。
  但会带来：规则不一致会破坏玩家的心智模型；求解器要为两种初始状态分别验证。

- **候选 D · 初始长度 1，但起点占两格（猫 + 备用格）**：
  能提供：折中方案。
  但会带来：概念复杂，玩家难以理解"备用格"是什么。

### 深度分析

判断标准是：**哪条规则能让"规则集最小"且"求解器验证最简单"？**

候选 B 引入的"初始朝向"是一个隐藏成本：它让关卡数据多一个字段，且这个字段出错会直接导致关卡无解。

候选 A 的关键优势：**第一次划线必定有效**（长度 1 时无蒲公英阻挡，除非正对墙或木箱子）。这让第 1 关的教学极其干净：玩家怎么划都有反应，立刻理解"滑到撞墙为止"。

用户补充：初始朝向可以默认向上。这简化了关卡数据——不需要额外字段，默认值统一即可。

### 综合判断

**采用候选 A：初始只有猫（占一格，位于关卡起点），默认朝向向上。**
关卡数据不需要初始朝向字段。蒲公英障碍规则在划线后自然生效。

## 问题：撞到已长出的蒲公英，是「停下」还是「判负」？

状态：user_confirmed

### 广度分析

- **候选 A · 停下（蒲公英即墙）**：划线滑行到蒲公英前一格停住，本步结束。
  能提供：玩家可以把自己的蒲公英当墙用——这是深度的来源（用蒲公英制造新的阻挡点）；失败只发生在"四向都动不了"。

- **候选 B · 判负（撞到即死）**：撞到蒲公英直接困死。
  能提供：紧张感更高。
  但会带来：玩家会倾向于保守走位；且"撞墙/木箱子停下、撞蒲公英却死"两条规则不一致，心智负担重。

- **候选 C · 撞到蒲公英停下，但立即判定是否还有解，无解则判负**：
  能提供：减少玩家在死局里空转的时间。
  但会带来：等于让系统替玩家判断"你输了"，剥夺了玩家自己发现死局的思考过程；且需要运行时求解器。

- **候选 D · 蒲公英可穿过**：
  能提供：更宽松的规则。
  但会带来：与"路径不可逆"的核心概念冲突；求解器复杂度上升。

### 深度分析

判断标准是：**蒲公英在本游戏中承担什么角色？**

拆解研究表明，Longcat 的身体有双重身份：**既是障碍，也是进度**。
候选 A 让这个双重身份成立——蒲公英是墙（障碍），但每多一朵蒲公英就意味着离通关更近（进度）。玩家会主动利用蒲公英制造转角，这是策略深度的主要来源。

候选 B 摧毁了这一设计：蒲公英变成纯惩罚源，玩家会规避它，而不是利用它。

候选 C 的致命问题是**它让系统替玩家解题**。本游戏的核心乐趣就是自己推演路径、自己发现死局。而且它需要运行时求解器，与架构决策冲突。

### 综合判断

**采用候选 A：蒲公英视同墙，滑行到它前面停下。**
失败只有一种：四向均无法产生有效移动且未填满。不提前宣告死局，不替玩家判断。

## 问题：无效移动（划线 0 格）如何处理？

状态：user_confirmed

### 广度分析

- **候选 A · 输入作废，不消耗回合，不改变任何状态**：
  能提供：零成本试探——玩家可以在想不清楚时用手指去试；且"掉头"这一场景被同一条规则自然覆盖。

- **候选 B · 消耗一步，但状态不变**：
  能提供：让"乱试"有代价。
  但会带来：本游戏无步数限制，消耗一步毫无意义；且会惩罚正常玩家的误操作。

- **候选 C · 输入作废，但给出提示反馈（如震动/抖动）**：
  能提供：让玩家明确知道"这个方向走不了"。
  但会带来：这属于呈现层的辅助反馈，需注意不要演变成"自动排除无效方向"。

- **候选 D · 额外设立「禁止掉头」规则单独处理反向输入**：
  能提供：规则表述更直白。
  但会带来：增加一条独立规则；且与"撞蒲公英停下"逻辑重复。

### 深度分析

判断标准是：**能否用最少的规则覆盖最多的场景？**

关键洞察：**候选 A 一条规则同时覆盖四个场景**：
1. 正对边界 → 路径 0 格 → 无效
2. 正对木箱子 → 路径 0 格 → 无效
3. 正对蒲公英 → 路径 0 格 → 无效
4. **反向掉头**（猫相邻格是自己长出的蒲公英）→ 路径 0 格 → 无效

第 4 点尤其优雅：**不需要单独的"禁止掉头"规则**，它是"蒲公英即墙"的自然推论。

用户补充：每关提供 3 次撤销机会（点击按钮回退上一步），给误操作玩家容错空间。这是一个独立于"无效移动"的机制——撤销是主动回退，无效移动是被动拒绝。

### 综合判断

**采用候选 A（+ 候选 C 的轻反馈）：划线路径为 0 格时，输入作废，不消耗回合，不改变任何状态。**
不设立独立的「禁止掉头」规则——它是「蒲公英即墙」的自然推论。
反馈限制：可给轻微撞击反馈，**禁止把无效方向置灰或阻止输入**（架构呈现契约第 3 条）。

**新增机制：每关 3 次撤销机会。** 点击撤销按钮，回退上一步操作（蒲公英消失，猫回到上一步位置）。每关最多 3 次，用完不可再用。

## 问题：是否需要星级评价？

状态：user_confirmed

### 广度分析

- **候选 A · 不需要评级，通关即可**：
  能提供：规则最简，玩家无压力；全覆盖谜题本身已足够有挑战。
  但会带来：无"做得好不好"的量化反馈。

- **候选 B · 基于步数比率评级（3星/2星/1星）**：
  能提供：鼓励玩家寻找最优解；为排行榜提供比较基准。
  但会带来：玩家可能为追求星级反复重试，增加挫败感。

### 深度分析

判断标准是：**星级评价是否与核心体验一致？**

用户指出：玩法是"通过滑动铺满全图"，理论上全覆盖谜题的解不唯一（存在多条合法路径），但解的数量决定难度。

关键洞察：**本游戏的核心体验是"我解开了这道题"，不是"我解得比别人快"。**

星级评价会引入"优化焦虑"——玩家会纠结"我能不能用更少步数通关"，这与"轻松解压"的定位冲突。

而且，社交比拼（每日挑战、排行榜）已经提供了"比较"的维度，不需要在单关层面再加星级。

### 综合判断

**采用候选 A：不需要星级评价，通关即可。**
社交比拼通过每日挑战与排行榜实现（P1），不在单关层面引入星级。

## 问题：关于"唯一解"的讨论

状态：user_confirmed

### 分析

全覆盖谜题（哈密顿路径问题）在大多数网格布局下**解不唯一**——存在多条合法路径都能铺满全图。

但这不影响游戏体验，反而是设计优势：
1. **重玩价值**：同一关可以走不同路线
2. **社交话题**：朋友之间可以讨论"你走的什么路线？"
3. **降低挫败感**：不唯一 = 玩家走的路和"标准答案"不同也能过

**真正影响难度的是"解的数量"：**
- 解越少 → 越难（分支稀缺，走错一步就进死胡同）
- 解越多 → 越简单（容错高，怎么走都能通）

### 结论

**不追求唯一解，但用解的数量控制难度。** 这也是 S02 用"解的数量"作为难度指标的原因。

## 问题：离线验证与运行时如何保证行为一致？

状态：user_confirmed

### 广度分析

- **候选 A · 各写一份**：离线工具用 Python/JS 独立实现，运行时用 TypeScript。
  能提供：各自可用最顺手的语言。
  但会带来：**两份实现必然分叉**，离线验证"有解"的关卡在运行时可能行为不同——内容护城河直接失效。

- **候选 B · 共用同一份 TypeScript 规则代码**：`core/` 层不依赖 Cocos，离线工具与运行时都 import 它。
  能提供：**行为一致的数学保证**；规则改动一次生效两处；`core/` 可跑 node 单测。

- **候选 C · 运行时调用离线服务（云端求解）**：
  能提供：只需一份实现。
  但会带来：需要后端；运行时网络依赖。

- **候选 D · 共用代码 + 定期回归比对**：
  能提供：双保险。
  但会带来：若已共用同一份代码，回归比对是冗余的。

### 深度分析

判断标准是：**内容护城河的前提是什么？**

本项目的护城河是「关卡可批量生成且 100% 可验证」。这个前提有一个隐藏依赖：
**验证器的行为必须与实际游玩的行为完全一致。**

如果离线求解器说"这关有解，解法是 ↑→↓←"，但运行时因为实现差异导致某一步滑行距离不同，那么提示功能会给错误提示，难度评分失真，最坏情况下出现"验证有解但实际无解"的关卡。

候选 B 是唯一能从**结构上**杜绝这个问题的方案：同一份代码，不可能分叉。

### 综合判断

**采用候选 B：`core/` 层为不依赖 Cocos 的纯 TypeScript，离线生成器/求解器与运行时游戏共用同一份规则代码。**

工程约束：
- `core/` 不得 import 任何 Cocos 模块、不得访问任何引擎 API、不得依赖运行时环境。
- `core/` 必须可用 `node` 直接跑单测。
- 任何规则改动只需改 `core/` 一处，离线与运行时同步生效。
