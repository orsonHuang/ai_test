# 08 · 技术选型与架构

## 1. 引擎选择

### 1.1 决策：Cocos Creator 3.8.x

| 选项 | 适配度 | 理由 |
|------|--------|------|
| **Cocos Creator 3.8.x** | ★★★★★ | 微信小游戏行业标准，TS 开发，原生导出，包体优化成熟 |
| Godot → HTML5 | ★★★☆☆ | 有经验但微信适配需额外工作，包体控制不如 Cocos |
| Laya | ★★★★☆ | 也适配微信，但社区不如 Cocos 活跃 |

**选择 Cocos Creator 的核心理由**：
1. 原生微信小游戏导出，零适配成本
2. TypeScript 开发，类型安全
3. 内置 TileMap 组件支持网格地图
4. 包体优化工具链成熟（纹理压缩、分包加载）
5. 个人开发者社区资源丰富

### 1.2 版本与工具链

| 工具 | 版本 |
|------|------|
| Cocos Creator | 3.8.x（LTS） |
| 语言 | TypeScript |
| 微信开发者工具 | 最新稳定版 |
| Node.js | 18 LTS |

## 2. 项目架构

### 2.1 架构原则

1. **数据驱动**：关卡数据全部 JSON，逻辑与数据分离
2. **逻辑/渲染分离**：寻路、状态机等核心逻辑纯 TS，不依赖引擎
3. **可迁移性**：核心逻辑层可移植到 Steam 版（替换渲染层即可）
4. **MVP 优先**：不过度抽象，先跑通再优化

### 2.3 分层架构

```
┌─────────────────────────────────┐
│         UI 层（Cocos 组件）       │  ← 按钮弹窗、物品栏、结算
├─────────────────────────────────┤
│      游戏逻辑层（Cocos 组件）     │  ← GameController、HeroController
├─────────────────────────────────┤
│      核心逻辑层（纯 TS）          │  ← PathFinder、GridMap、GameLogic
│         （可独立测试/迁移）        │
├─────────────────────────────────┤
│      数据层（JSON）               │  ← 关卡数据、配置
└─────────────────────────────────┘
```

**关键**：`core/` 目录下的代码**不依赖 Cocos 引擎**，纯 TypeScript 实现。这保证：
- 可用 Node.js 直接跑单元测试（无需启动引擎）
- Steam 版迁移时，核心逻辑层原样复用，只替换上层

## 3. 核心模块设计

### 3.1 PathFinder（A* 寻路）

```typescript
// core/PathFinder.ts（纯 TS，无引擎依赖）

interface Point { x: number; y: number; }
interface PathResult {
  path: Point[];        // 路径格子序列
  length: number;       // 路径长度
  hasPath: boolean;     // 是否存在路径
  dangerSegments: Array<{  // 危险段标注
    index: number;      // 在 path 中的位置
    type: 'trap' | 'vision';
  }>;
}

class PathFinder {
  // 根据当前网格状态计算最短路径
  findPath(grid: GridMap, start: Point, goal: Point): PathResult;
  
  // 传送门特殊处理：入口的邻居包含出口
  private getNeighbors(grid: GridMap, p: Point): Point[];
  
  // A* 核心算法
  private astar(grid: GridMap, start: Point, goal: Point): Point[];
}
```

**性能目标**：12×12 网格 + 5 个物品，寻路 < 10ms。

### 3.2 GridMap（网格数据）

```typescript
// core/GridMap.ts

enum CellType {
  Ground,      // 普通地面（可通行，安全）
  Wall,        // 墙壁（障碍）
  Trap,        // 陷阱（可通行，致命）
  Stone,       // 石头（障碍，玩家放置）
  PortalIn,    // 传送门入口（可通行，特殊）
  PortalOut,   // 传送门出口（可通行）
  Guard,       // 守卫本体（障碍）
  GuardVision, // 守卫视野（可通行，致命）
  GuardBack,   // 守卫背后（可通行，安全）
  DemonKing,   // 魔王（障碍，目标）
}

class GridMap {
  cells: CellType[][];
  width: number;
  height: number;
  
  isPassable(x: number, y: number): boolean;  // 障碍判定
  isDangerous(x: number, y: number): boolean;  // 致命判定
  isSafe(x: number, y: number): boolean;       // 安全判定
  
  // 放置/移除物品后更新网格
  placeStone(x: number, y: number): void;
  placePortal(a: Point, b: Point): void;
  removeItem(x: number, y: number): void;
}
```

### 3.3 GameLogic（状态机）

```typescript
// core/GameLogic.ts

enum GameState {
  Preparing,   // 准备阶段
  Executing,   // 执行阶段
  Victory,     // 胜利
  Defeated,    // 失败
}

enum DefeatReason {
  Trap,        // 踩陷阱
  Vision,      // 进守卫视野
  DeadEnd,     // 死胡同
}

class GameLogic {
  state: GameState;
  grid: GridMap;
  currentPath: PathResult;
  placedItems: PlacedItem[];
  
  // 准备阶段
  placeItem(item: Item, pos: Point): boolean;  // 返回是否合法
  removeItem(pos: Point): void;
  recalculatePath(): void;  // 放置/移除后调用
  
  // 执行阶段
  startExecution(): void;
  step(): void;  // 勇者走一步 + 检查事件
  
  // 结果
  onVictory: () => void;
  onDefeat: (reason: DefeatReason) => void;
}
```

### 3.4 LevelSolver（关卡求解器）

```typescript
// core/LevelSolver.ts（Node.js 可独立运行）

class LevelSolver {
  // 验证关卡是否有解
  hasSolution(level: LevelData): boolean;
  
  // 计算最优解（最少物品数）
  findOptimalSolution(level: LevelData): {
```

## 4. 数据流

```
准备阶段：
  玩家放置物品 → ItemController → GameLogic.placeItem()
      → GridMap 更新 → PathFinder.findPath() → PathResult
      → PathRenderer 更新虚线 → UI 更新物品栏数量

执行阶段：
  GameLogic.startExecution() → 逐格 step()
      → HeroController 移动勇者 → 检查格子事件
      → 陷阱/视野 → onDefeat → ResultDialog
      → 魔王相邻 → onVictory → ResultDialog
```

## 5. 性能与包体

### 5.1 包体目标

| 项目 | 目标 | 手段 |
|------|------|------|
| 主包 | ≤ 4MB | 核心代码 + 首页素材 |
| 总包 | ≤ 20MB | 分包加载关卡数据 + 素材 |
| 单关卡 JSON | < 5KB | 精简数据结构 |
| 纹理 | WebP + TexturePacker | 压缩 + 合图 |

### 5.2 性能目标

| 指标 | 目标 |
|------|------|
| 寻路计算 | < 10ms（12×12 网格） |
| 路径更新 | < 50ms（含渲染） |
| 帧率 | 60fps（执行阶段） |
| 内存 | < 100MB |

### 5.3 网格规模限制

MVP 限制 ≤ 12×12 = 144 格，保证：
- 寻路毫秒级
- 求解器暴力搜索可行
- 屏幕显示清晰（竖屏单屏可见）

## 6. Steam 版迁移预留

### 6.1 可复用部分

| 层级 | 可复用 | 说明 |
|------|--------|------|
| 核心逻辑层（core/） | ✅ 100% | 纯 TS，无引擎依赖 |
| 关卡数据 JSON | ✅ 100% | 数据格式不变 |
| 游戏逻辑层（game/） | ⚠️ 部分 | 需替换 Cocos 组件为 Steam 引擎组件 |
| UI 层 | ❌ 重写 | Cocos UI → Steam UI 框架 |

### 6.2 迁移策略

1. 核心逻辑层（`core/`）保持纯 TS + 零引擎依赖
2. 游戏逻辑层通过接口抽象，渲染层可替换
3. 关卡数据格式向前兼容（版本号字段）
4. Steam 版可考虑迁移到 Godot 4 或继续用 Cocos（PC 导出）

### 6.3 Steam 版新增技术需求（V2）

- 云存档
- 成就系统（Steam Achievements）
- 创意工坊（关卡编辑器 + 上传/下载）
- 手柄支持
- 更高分辨率素材（128px 格子）
