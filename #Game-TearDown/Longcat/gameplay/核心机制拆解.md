# Longcat · 核心机制拆解

## 一、规则的形式化描述

把官方描述翻译成可实现的状态机。这是本次拆解中**对开发最直接有用的部分**。

### 1.1 状态定义

```
Grid      : 二维网格，每格 ∈ {EMPTY, WALL, BODY}
Body      : 有序格序列 [head, ..., tail]，初始长度 = 1 或 2 [推断]
HeadPos   : Body[0]
Direction : ∈ {UP, DOWN, LEFT, RIGHT}
```

### 1.2 单次输入的结算流程

```
on_input(dir):
    # ① 合法性检查：不能直接掉头
    if dir == opposite(LastDirection):        # [推断] 依据：官方解法序列中从不出现相邻反向
        return REJECTED

    # ② 滑行：逐格推进直到受阻
    path = []
    cur  = HeadPos
    while true:
        next = cur + dir
        if not in_bounds(next):  break       # 撞边界
        if grid[next] == WALL:   break       # 撞墙
        if grid[next] == BODY:   break       # 撞自己身体/尾巴
        path.append(next)
        cur = next

    # ③ 无效移动判定：一格都没推动 → 输入作废，不消耗回合
    if path.is_empty():
        return REJECTED

    # ④ 提交：路径上的格子永久固化为身体
    for cell in path:
        grid[cell] = BODY
    Body.prepend(path)

    # ⑤ 胜负判定
    if count(EMPTY) == 0:
        return WIN
    else if no_legal_move_exists():          # 四向全部 REJECTED
        return LOSE_STUCK
    else:
        return CONTINUE
```

### 1.3 三条硬规则 + 两条边界

| # | 规则 | 说明 |
|---|------|------|
| R1 | **滑行到底** | 一次输入 → 滑到撞墙/撞身体才停，玩家无法中途停 |
| R2 | **轨迹永久固化** | 滑过的空格变成身体，不可逆（除非重开关卡） |
| R3 | **身体即障碍** | 尾巴和身体都算墙，撞上即停 |
| B1 | **无效移动不消耗回合** `[推断]` | 若某方向一格都推不动，输入作废，不算一步 |
| B2 | **禁止直接掉头** `[推断]` | 反方向输入会被拒绝（会立刻撞到自己第二节） |

> B1/B2 推断依据：Fancade Wiki 公布的 1–50 关官方解法序列中，**从未出现相邻两步为反向**的情况（如 `↑` 后紧跟 `↓`），且总步数恰好等于填入格数所需的移动次数。

### 1.4 胜利 / 失败条件

```
胜利  = 所有非墙格全部被身体填满（覆盖率 100%）
失败  = 存在空格，但四个方向全部无法产生有效移动（困死）
```

**注意这个失败定义的狠处**：它不是"步数用尽"或"血量归零"，而是**玩家自己把自己堵死了**。失败的责任完全在决策，不在系统——这正是玩家愿意反复重试的心理基础。

## 二、机制归类：为什么它不是贪吃蛇

表面看是"贪吃蛇换皮"，实际是三个根本差异：

| 维度 | 贪吃蛇 | Longcat |
|------|--------|---------|
| 移动粒度 | 一格一格，实时持续 | 一次输入 = 一段可变长位移，回合制 |
| 节奏 | 实时推进，有时间压力 | **完全无时间限制**，纯回合思考 |
| 身体增长 | 吃道具才长，尾部会回收 | **滑多远长多长，永不回收** |
| 身体作用 | 主要是"别撞到"的惩罚源 | **双重身份：既是障碍，也是进度** |
| 目标 | 生存 + 刷分（无限） | 全覆盖（有限、有唯一解） |
| 关卡性质 | 一张图反复玩 | 每关一次性谜题 |

**最关键的一条**：贪吃蛇是**操作游戏**（考验反应和路径规划的实时执行），Longcat 是**谜题游戏**（考验空间推理的离线规划）。

---

## 三、谜题本质：受限的哈密顿路径

### 3.1 数学表述

> 在网格图 G 上找一条路径 P，使得 P 覆盖所有非墙顶点且不重复，
> 同时路径必须能被**切分成若干段直线**，每段直线的终点必须是"墙或已提交路径"。

这就是**增量式哈密顿路径问题**（Incremental Hamiltonian Path）。

### 3.2 这个性质带来三个工程级好处

| 好处 | 含义 | 对新项目的价值 |
|------|------|--------------|
| **可解性可离线验证** | 写个 DFS/BFS 求解器就能判定关卡有没有解 | 自动生成关卡的必备前置 |
| **难度可量化** | 解的数量、最短解步数、分支因子 → 直接当难度指标 | 不用靠设计师手感排序关卡 |
| **解的唯一性可控** | 调整墙的分布可以逼近"唯一解" | 想要"硬谜题"还是"宽容谜题"可调 |

### 3.3 分支因子陷阱

真正决定难度的**不是步数，是分支稀缺度**——即"走错一步之后，还剩多少条活路"。

实证（见 `numbers/`）：第 15 关只需 **8 步**，却排在需要 14 步的第 14 关之后；第 40 关 12 步，第 46/47 关 13/12 步。
**短关卡可以比长关卡难**——因为它的活路更少。

## 四、「步长不由玩家决定」的连锁后果

这一条取舍是 Longcat 的设计内核，值得单独拆：

```
玩家控制权 ↓ （只剩 4 个离散输入）
      ↓
├─ 操作失误归零      → 失败只能归因于决策 → 玩家愿意重试
├─ 关卡 = 确定性谜题  → 可生成、可验证、可量化难度
├─ 生产重心转移      → 从"做系统"转到"做关卡"
├─ 单指即可游玩      → 移动端 / 小程序天然适配
└─ 无需教程          → 第 1 关就是教程，零文字说明
```

**风险面**（对新项目的警示）：

| 风险 | 表现 | 缓解思路 |
|------|------|---------|
| 内容消耗极快 | 1900 关听起来多，玩家一天能刷 100 关 | 加每日挑战、排行榜、编辑器 |
| 卡关即流失 | 没有成长系统接住挫败感 | 加提示/跳过、或加元层成长 |
| 缺乏重玩价值 | 关卡解完即弃 | 加"最短步数"星级、重玩挑战 |
| 极易被抄 | 规则简单，抄袭成本低 | 靠内容量和品牌，不靠机制保密 |

## 五、待验证清单（需实玩确认）

| # | 待验证项 | 验证方式 | 影响 |
|---|---------|---------|------|
| 1 | 网格是纯 2D 逻辑 + 3D 呈现，还是含高低差的真 3D 多层？ | 实玩观察是否有上下层 | 决定关卡数据结构与渲染方案 |
| 2 | 初始身体长度是 1 还是 2？ | 看第 1 关起始画面 | 影响解算器初始状态 |
| 3 | 是否存在"撤销上一步"功能？ | 玩错一步看 UI | 影响难度与挫败感设计 |
| 4 | 是否有提示 / 跳过关卡？ | 卡关时看 UI | 影响留存设计 |
| 5 | 撞到自己身体时，是"停下"还是"判负"？ | 故意撞自己 | **关键**：官方描述说"停下"，需确认 |
| 6 | 1900+ 关中，手工设计与程序生成的比例？ | 对比前 50 关与后续关卡风格 | 决定生成器投入 |
