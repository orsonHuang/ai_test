# Longcat 拆解 → 微信小游戏项目启示

> 目标项目：**Cocos Creator + MCP 辅助开发 + 微信小游戏** · 滑行填充解谜方向
> 本文把 Longcat 的拆解结论，翻译成新项目的技术与范围决策。

---

## 一、微信小游戏的硬约束（架构级影响）

| 约束 | 数值 `[需以最新官方文档核实]` | 对本项目的直接影响 |
|------|---------------------------|------------------|
| **主包大小** | 4 MB | 代码 + 首屏资源必须极精简 |
| **分包总大小** | 20 MB | 美术资源走分包 |
| **远程加载** | 无硬上限（走 CDN） | **关卡数据必须远程化** |
| **本地缓存** | 200 MB（wx 文件系统） | 关卡可缓存，减少重复拉取 |
| **提审周期** | 1–7 天 | 内容更新绝不能走提审 |
| **内购资质** | 无版号不可开虚拟支付 | 变现以广告为主 |
| **启动性能** | 首屏渲染越快越好 | 体素风格天然友好 |

### 最关键的一条：关卡数据必须远程化

```
❌ 错误：1900 关打进小游戏包 → 超包体 + 每次加关都要提审
✅ 正确：关卡 JSON 放 CDN/云开发，启动时按章节拉取 + 本地缓存
```

**这条约束直接决定了三件事**：
1. 关卡用轻量 JSON 字符串（见 `systems/关卡系统.md` 第三节），不用场景文件
2. 需要一个简单的版本号 / 增量更新机制
3. 离线缓存策略：已玩过的章节缓存本地，未玩的按需拉取

## 二、Cocos Creator 技术要点

### 2.1 为什么 Cocos 适合这类游戏

| 需求 | Cocos 的支撑 |
|------|-------------|
| 微信小游戏发布 | ✅ 一等公民，官方构建模板 |
| 2D 网格渲染 | ✅ 轻量，TileMap / Sprite 均可 |
| 包体控制 | ✅ 引擎可裁剪，2D 空包 ~1MB |
| TypeScript | ✅ 类型安全，适合网格/求解器逻辑 |
| 热更 | ✅ 支持（但关卡走远程更简单） |

### 2.2 建议的技术分层

```
assets/
├── scripts/
│   ├── core/            # 纯逻辑层，不依赖 Cocos（可单测）
│   │   ├── Grid.ts          # 网格数据结构
│   │   ├── SlideRules.ts    # 滑行结算（对应核心机制拆解 1.2）
│   │   ├── Solver.ts        # 求解器（DFS + 剪枝）
│   │   └── LevelLoader.ts   # 远程关卡加载 + 缓存
│   ├── game/            # 游戏层，依赖 Cocos
│   │   ├── CatView.ts       # 猫身渲染
│   │   ├── InputManager.ts  # 滑动手势 → 方向
│   │   └── GameController.ts
│   └── meta/            # 元层（进度/广告/分享/排行）
└── resources/
    └── levels/          # 仅内置前 20 关（教学 + 首屏体验）
```

**关键决策：`core/` 层不依赖 Cocos 引擎。**
理由：求解器和规则逻辑是最需要测试、最容易出 bug 的部分，纯 TS 可以直接跑 node 单测，
也能**复用为离线的关卡生成器/验证器**（一份代码，两处用）。

### 2.3 待核实事项

- [ ] Cocos Creator 版本号（3.7 / 3.8 影响 MCP 插件选择，见下）
- [ ] 微信小游戏最新的包体/分包上限
- [ ] 是否需要微信云开发（关卡数据托管 + 排行榜，可减少后端工作量）

## 三、MCP 辅助开发的工作流设计

用户指定「基于 MCP 开发」。Cocos 生态现有的 MCP 方案（**待 Orson 确认选哪个**）：

| 方案 | 要求 | 特点 |
|------|------|------|
| **Funplay MCP for Cocos** | Cocos Creator 3.8+ | 开源；编辑器内起本地 MCP Server；可查场景/节点/组件/资源/日志/截图；支持构建、预览、场景保存、Button 事件绑定 |
| **cocos-mcp-server** | Cocos Creator 3.7.0+ | 商店插件（V1.7.7）；放 `extensions/` 目录；默认端口 3000；有面板开关 |
| **Cocos Agent** | — | 不是纯 MCP 工具集，是基于 OpenCode 的 Cocos 专属 AI Harness；含渲染管线/Text-to-3D 等重功能 |

### 建议的工作流分工

```
                    ┌──────────────────────┐
                    │   AI（本工作区）      │
                    └──────┬───────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  【文件系统层】      【Cocos MCP 层】     【离线工具层】
  写 .md 文档       查看/修改场景节点     跑求解器
  写 core/*.ts      读日志、截图         批量生成+验证关卡
  写 GDD            触发构建/预览        导出关卡 JSON
  更新索引          绑定组件/事件        上传 CDN
```

**核心原则**：
- **规则和求解器这类纯逻辑，AI 直接写文件**（不经过 MCP，更快、可版本控制）
- **场景搭建、节点挂载、构建预览，走 Cocos MCP**（需要真实编辑器上下文）
- **关卡生成/验证用独立 node 脚本**（批量、可离线跑，不占用编辑器）

### MCP 能带来的最大收益（针对本项目）

1. **AI 能看到编辑器里的真实截图** → 可以自查渲染问题（网格错位、猫身断裂）
2. **AI 能读运行日志** → 定位滑行逻辑 bug
3. **AI 能触发构建预览** → 快速迭代

## 四、首版范围建议（P0 最小闭环）

基于 Longcat 拆解，我认为 MVP 应该这么切：

### 必须做（P0）

| 模块 | 范围 | 依据 |
|------|------|------|
| 核心机制 | 滑行到底 + 轨迹固化 + 困死判定 | Longcat 地基 |
| 关卡 | **手工 20 关**（教学 5 + 简单 8 + 普通 7） | 前 20 关手工保证第一印象 |
| 交互 | 单指滑动 + 一键重开 | UX 核心 |
| 渲染 | 纯色方块 + 猫身，无特效 | 可读性优先（P7） |
| 进度 | 本地存储 + 关卡选择 | 最小进度感 |
| 撤销 | ✅ 必须有 | Longcat 的明显缺陷 |

### 应该做（P1）

| 模块 | 理由 |
|------|------|
| **关卡生成器 + 求解器** | ⚠️ 建议在 P0 末就启动，不要等关卡不够用 |
| 微信分享 / 群排行榜 | 微信独有红利 |
| 激励视频（提示 / 跳过） | 变现 + 接住卡关玩家 |
| 每日挑战 | 低成本高留存 |

### 暂缓（P2+）

| 模块 | 理由 |
|------|------|
| Roguelike 元层 | 差异化核心，但需先验证基础玩法 |
| 特殊方块（冰块/传送门） | 机制变体，需先跑通基础 |
| 关卡编辑器 | 重功能，看用户量再定 |
| 皮肤系统 | 需内容积累 |

### 建议的里程碑

```
M1  核心机制可玩（10 关手工）        → 验证"好不好玩"
M2  Cocos MCP 打通 + 微信真机预览    → 验证技术链路
M3  求解器 + 生成器跑通（100 关）    → 验证内容产能
M4  微信提审上线（150 关 + 广告位）  → 验证数据
M5  差异化元层（Roguelike / 每日）   → 拉开与同类差距
```

## 五、风险清单

| 风险 | 等级 | 说明 | 应对 |
|------|------|------|------|
| **玩法抄袭感** | 🔴 高 | 机制与 Longcat 高度重合 | 至少做一个机制变体 + 一个元层差异 |
| **求解器性能爆炸** | 🔴 高 | 网格稍大就指数爆炸 | 网格限 8×10 内 + 强剪枝 + 大网格改用启发式 |
| **超包体** | 🟡 中 | 美术/音频累积 | 关卡远程化 + 资源分包 + 程序化音效 |
| **提审被拒** | 🟡 中 | 小游戏类目/广告资质 | 提前查类目要求 |
| **MCP 插件版本不兼容** | 🟡 中 | Cocos 版本与 MCP 要求不匹配 | 先确认 Cocos 版本再选插件 |
| **内容消耗过快** | 🟡 中 | 玩家数天刷完 | 每日挑战优先于堆关卡 |
| **无版号只能靠广告** | 🟢 低 | ARPU 天花板 | 设计时就预留广告位 |

## 六、一句话总结

**Longcat 证明了"滑行填充"是一个验证过的、可批量生产内容的、天然适配移动端的玩法地基。
但它把复杂度全部压在关卡上、局外几乎裸奔——这既是它的优雅，也是它留给后来者的空地。**

新项目的机会不在"做得更像 Longcat"，而在：
1. **接住它没接住的玩家**（提示/撤销/跳过/成长）
2. **拿它没拿的红利**（微信社交裂变）
3. **补它刻意放弃的深度**（元层 / 机制变体）
