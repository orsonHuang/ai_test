## 分类与分析框架

### 分类采用独立维度

商业化与单机存在交叉，不能作为互斥的一级类型。游戏档案分别记录下列维度，并据此选择拆解重点；同一款游戏可以同时使用两种分析视角。

| 维度 | 建议记录内容 | 用途 |
|------|--------------|------|
| 游玩形态 | 单人、多人合作、多人竞争；是否依赖联网，按实际情况记录 | 判断系统的交互环境、竞争与社交依赖；单人与离线不等同 |
| 商业模式 | 买断、免费内购、广告、订阅/时长付费、DLC/扩展包、混合；允许多选或未核实 | 分析收入来源及其与系统规则的关系 |
| 运营方式 | 完整作品交付、内容扩展、赛季/活动驱动、持续服务；可并存 | 判断内容节奏、系统生命周期与维护要求 |
| 研究范围 | 平台、地区/服、版本、观察日期、玩家阶段 | 避免不同版本和进度的规则混用 |

不得根据 PC/手机、单人/多人直接推断商业模式。未知值记为「未核实」，不当作「没有」或筛选命中。

### 通用底座与两种分析视角

所有游戏都分析定位、核心体验、玩法循环、系统全景、操作流程、规则、反馈、系统关联、玩家代价与迁移条件。在此基础上增加对应分析重点。

| 主题 | 长线运营与商业化视角 | 单机与完整体验视角 |
|------|----------------------|--------------------|
| 核心目标 | 长期参与、玩家分层、经济运转及收入如何与体验共存 | 核心体验能否成立，内容是否完整，游玩是否有满足感 |
| 节奏 | 日/周循环、赛季、活动、回流与阶段性目标 | 学习、探索、难度、叙事、高潮、结局或开放式终局 |
| 养成 | 成长线、资源来源与消耗、追赶、付费影响、版本膨胀 | 能力解锁、构筑分支、成长反馈、通关与重玩价值 |
| 经济与付费 | 货币循环、稀缺性、付费点、免费与付费体验差异 | 定价与内容承诺、扩展包边界、游戏内资源对决策的作用 |
| 系统负担 | 重复任务、时间门槛、库存压力、竞争压力如何影响体验 | 操作摩擦、流程打断、失败成本、重复内容是否必要 |
| 验证依据 | 可观察规则、公开资料与实际反馈；留存/收入没有数据则保持未知 | 试玩行为、规则与内容证据；完成率/时长等没有数据则保持未知 |

「长线商业化」与「单机体验」是可组合的研究视角，不是游戏品质等级。单机也分析商业目标；商业化游戏也完整分析玩法和体验。机制存在不等于已经证明它提升留存、付费或满意度。

### 系统模块的差异化分析

每个模块使用通用图文结构：定位 → 操作流程 → 核心规则与边界 → 系统关联 → 设计收益与代价 → 适用/不适用条件 → 迁移建议 → 来源与未核实项。

| 模块 | 长线商业化视角的附加问题 | 单机体验视角的附加问题 |
|------|--------------------------|------------------------|
| 背包 | 扩容是否收费？容量与掉落、收集、出售、回收如何联动？对不同玩家的整理成本如何？ | 容量/重量/形状是否制造有意义的取舍？整理是否打断体验？空间组合是否承担核心玩法？ |
| 竞技场/挑战场 | 匹配、排名、赛季、奖励、参与次数及付费强度如何关联？ | 若存在：对手是 AI 还是其他玩家？挑战节奏、难度梯度和奖励是否服务主体验？ |
| 养成 | 资源缺口、重复获取、成长上限、追赶与版本更新如何作用？ | 成长是否改变决策？构筑是否有分支？能否支撑通关、终局或重玩？ |

只分析游戏实际存在的模块；「未发现资料」「确认不存在」「不在本次范围」分别标记。系统案例保留商业模式、游玩形态和运营方式的关联字段，以便跨游戏检索。

### 图文与评价标准

- 每个系统案例围绕具体规则配置界面总览、关键操作截图、机制示意图或系统关系图；图量按解释需要决定。
- 区分原游戏截图、标注截图与原创机制示意图；每张图记录来源、版本/日期、必要的视频时间点及图注，指明它支撑哪条说明。
- 缺少原始界面证据时记录缺口；可以绘制标明「示意」的机制图，不能把推测界面当作原游戏截图。
- 「优秀」必须说明评价目标：例如操作效率、策略深度、可理解性、长期经济或体验完整性。设计收益、玩家代价、实现/运营成本、适用条件分别描述。
- 机制事实、分析推断和待验证假设分开写；成本未测量时只给带依据的估计，不编造内部指标。
- 未来网页支持按系统类型、商业模式、游玩形态、运营方式和模块专属机制筛选。收藏落到具体系统案例，可附用途和个人笔记。此处约定内容要求，不代表当前网页已支持这些功能。

## 工作规则

1. **一游戏一文件夹**：每个游戏在根目录下独占一个以游戏名命名的子文件夹（如 `三国-谋定天下/`）。
2. **命名约定**：游戏名优先用中文原名，多词用连字符 `-` 连接；有官方英文名可在文件夹内 README 注明。
3. **每个游戏文件夹必须包含 README.md**（该游戏的 INDEX），记录游戏基本信息、拆解范围、目录结构、当前进度。
4. **拆解产物的统一结构**：建议每个游戏文件夹内按以下子目录组织（按需创建，不必一次性全建）：
   - `overview/` — 游戏基本信息、背景、定位、核心卖点
   - `gameplay/` — 核心玩法循环、系统拆解
   - `systems/` — 具体系统分析（战斗/养成/社交/商业化等）
   - `numbers/` — 数值、成长曲线、经济系统分析
   - `ux/` — 界面、交互、用户体验分析
   - `notes/` — 零散笔记、观察、灵感
5. 分析以 `#LLM-WIKI/` 中的方法论为参考，产出结论优先，避免堆砌流水账。
6. 本库是 `#LLM-WIKI` 的案例实证来源：当方法论需要具体游戏案例支撑时，回查本目录。
7. 案例反哺方法论：拆解中验证或打破某条方法论时，将「实证结论」回写至 `#LLM-WIKI` 对应 domain/wiki，形成闭环。触发标准：
   - **验证类**：某条方法论在真实游戏中得到印证 → 在 wiki 对应页面补一条 `案例佐证`。
   - **打破类**：某条方法论不适用/被反例 → 在 wiki 页面标注 `反例` 或 `边界条件`。
   - 回写时走 `#LLM-WIKI` 自身的 Ingest/审核流程，保持方法论层纯净。

## 目录结构

```
Game-TearDown/
├── README.md                  # 本文件（项目 INDEX）
└── <游戏名>/                  # 每个游戏一个文件夹
    ├── README.md              # 该游戏的 INDEX
    ├── overview/              # 游戏基本信息与定位
    ├── gameplay/              # 核心玩法循环与系统拆解
    ├── systems/               # 具体系统分析
    ├── numbers/               # 数值/经济系统
    ├── ux/                    # 界面与交互体验
    ├── assets/                # 案例配图、标注图与原创机制图（按需创建）
    └── notes/                 # 零散笔记与灵感
```

## 注意事项

- 拆解分析属于学习沉淀，优先追求「可复用的结论」，而非简单罗列。
- 按用户的图文案例要求，配图与文字分析共同沉淀，替代旧版仅文字约定；保留图片来源与用途，区分研究材料和拟公开展示材料，不搬运整包游戏素材。
- 旧案例逐步补充分类、模块结构与配图，不因框架更新自动认定旧结论已重新核实。
