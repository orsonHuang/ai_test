# 生产流程与证据标准

## 输入与范围

最低输入为游戏名与研究目标。平台／地区／服／版本会改变规则时先问；用户已有指定则沿用。没有精确构建号时记录“公开资料研究，截至某日，构建号未核实”，不可包装成最新版本实测。

整游研究先建立系统地图；单系统研究只补足理解所需的游戏上下文。每个系统记录 `已证实存在 / 未核实 / 确认不存在 / 不在范围`。完整地图意味着逐类核查和公开缺口，不意味着凭常识把每类系统都填成存在。

## 资料源与取证

| 来源 | 适合证明 | 限制 |
|---|---|---|
| 用户提供的实机截图／录屏／操作记录 | 当前账号、平台、进度下的流程与界面 | 一次操作不能证明概率、所有玩家或隐藏规则 |
| 官方游戏内说明、规则公告、版本日志 | 明文规则与变更 | 记录发布日期和适用服；历史公告不自动代表当前规则 |
| 官方商店、开发者访谈 | 产品定位、平台、宣传承诺 | “三分钟一局”“轻松”等不是实测结果 |
| 官方转载玩家攻略 | 具体机制、构筑与原图线索 | 仍是玩家观点，不因为官方排版而变成官方验证 |
| 原作者攻略、公开实机视频 | 操作证据、玩家策略与困难 | 标作者、时间点、版本；不能从标题推导内容 |
| 评测／论坛反馈 | 待验证的体验问题 | 单条反馈不代表普遍比例；与机制事实分开 |

先检索官方／一手材料，再定向补机制缺口。搜索摘要用于定位页面，正文与图片实际打开后才入证据台账。无法访问则保留线索，不标已读。不同平台不默认共用规则；官网共用介绍可说明产品定位，但具体微信端价格、广告、掉落和付费规则需要微信端证据。

每条来源至少记录 ID、标题、URL、作者／发布主体、发布时间（未知可空）、访问日期、适用平台、版本范围、支持的事实、不能证明的内容。更新时保留旧结论适用版本，而不是用新版本覆盖历史。

## 事实与解释

- **事实 F**：可回到具体来源或操作记录。例：一个圣物有多种插槽效果。
- **推断 I**：从事实解释设计作用。例：换槽可能让掉落在不同构筑中继续有用。给出成立条件与反例。
- **建议 P**：迁移到新项目的设计／工程方案。明确这是参考实现，不能称原作源码或内部架构。
- **未知 U**：概率、容量、匹配算法、收益上限、隐藏保底等没有证据。列下一步采证办法。

未知不填 0；未发现不写“没有”；有付费不等于付费驱动全部体验；有某机制不等于已证明提升留存／收入。

## 图文生产

每篇系统正文至少有能解释其规则的图或流程。重点案例优先组合：入口与布局实图、操作前后对照、规则／状态图。

图片分为 `original-screenshot / annotated-screenshot / original-diagram / official-promo`。记录本地或远程路径、来源 ID、作者、版本／日期、图注、支持的事实 ID、公开状态。宣传图只能证明其展示内容，不能证明所有界面操作。

原创图必须注明“机制示意／分析图”；事实箭头与建议流程区分。缺少数据不画伪造数值曲线。截图保留必要上下文，标注不遮挡关键数值；不以 AI 生成界面冒充实机。图片公开状态为 `original / authorized / reference-only / unresolved`；后两者不进入默认公开媒体包。

## 产出和质量门槛

1. 建立范围、来源台账与系统地图。
2. 按证据写事实层，再写机制解释、取舍、迁移条件。
3. 每个系统独立成文；按需细分子系统，避免一页百科塞入所有模块。
4. 添加图文、岗位导航、结构化索引。
5. 检查链接、ID、平台、事实引用、图注；再做人读审查。

状态分别记录：`draft`（内容待补）、`researched`（资料级拆解）、`observed`（有适用实机观察）、`reviewed`（已完成所声明范围的内容复核）。发布是另一个字段，不能把 researched 自动等同于公开发布。

优质案例必须回答：它解决谁的什么问题？如何工作？付出什么代价？换到什么项目会失效？用什么可观察结果验证借鉴是否成功？不采用无法解释的“优秀 9.8 分”。

## 持续填充

以后提供“游戏＋平台＋目标系统”即可触发研究。新增材料先检查是否改变既有事实，再更新对应系统及其索引；同一系统 ID 保持稳定。每次记录新来源、变更规则和未解决问题。网页收藏引用 ID，修订保留 revision；已收藏旧版仍能知道发生了什么变化。
