# 游戏系统图文拆解

将游戏研究沉淀成可独立阅读、检索、对比和收藏的模块专业设计文档。

## 范围与入口

- 若工作区有 `#Game-TearDown/README.md`，先读它及目标游戏 README；按其规则写入内容生产端。没有此库时使用用户指定目录，不创建无关仓库。
- 用户指定的平台、版本、DLC、系统和深度优先；只有影响结论的范围不清时才问。可独立进行的模板／资料定位工作继续。
- 整游拆解输出游戏档案、三层循环、系统地图、逐系统正文和岗位导航。单系统拆解只补理解它所需的游戏背景。增量更新保留案例 ID 和历史适用范围。
- 游玩形态、商业模式、运营方式独立记录；商业化与单机视角可组合。未核实不等于没有。

## 研究与写作

1. 打开实际来源，记录平台、版本、发布日期及访问日期；官方商店仅支持产品承诺，不证明实测体验。微信小游戏与 App 不默认同规则。
2. 建系统地图，区分存在／未核实／确认不存在／不在范围。阅读 [模块问题](references/module-questions.md) 中相关类型，不把清单中的所有模块强加给游戏。
3. 写可核实事实，再写分析推断和迁移建议。截图、规则与视频时间点关联具体事实；没有留存、收入、概率、源码等证据就保留未知。
4. 写作前读 [作者正文与排版](references/reader-writing.md)。公开正文以作者分析视角解释玩法、选择与代价；开发规格放独立附录。按 [输出约定](references/output-contract.md) 补齐目标边界、对象、流程、规则、数据配置、状态异常、系统接口、UI/美术反馈和验收。规则 ID 与测试 ID 用于附录追踪，不挤入公开标题；原作未知项不强填，复现所需补充明确标为参考设计。重点系统加入操作前后或状态图；原创图标明示意，不能伪造原游戏界面。
   本库用户已选择“可直接开发的参考设计”：保留原作未知，同时在 P 轨为明确的参考版本补齐默认参数、计算顺序、状态转换与异常处理。其他项目先沿用其已确认深度；不得把 P 参数写进事实标签。演示配置达到可实现不等于完整商业内容或原型测试已经通过。
5. 增加策划／开发／美术入口。原作规则与参考实现分开；开发状态表、美术资产建议不能冒充原作内部资料。
6. 校验引用、图片来源、平台一致性、正文路径与案例 ID；再人读检查“为什么有用、有什么代价、何时不适用”。若项目已有验证器，运行相关检查。

## 交付边界

资料级分析可以交付，但要显示证据成熟度和影响结论的缺口。不要以空模板、来源链接清单或未查看的图片替代实际拆解。缺少证据时说明还需要观察什么，不编写看似完整的虚构机制。

图片区分实机／标注／原创示意／宣传图。仅明确可公开的媒体进入发布包；引用材料保留链接。用户要求分析不等于要求部署网页、付费购买、修改游戏账号或替其发布内容。

更新后列出新增／修订案例、证据级别、关键缺口和可复现的检查结果。网页与 Skill 是否已安装或发布，只根据工具结果报告。
