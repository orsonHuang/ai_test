# 输出约定

在 Game-TearDown 库内使用 `_framework/字段与检索规范.md` 与 templates 的最新规范；以下用于脱离原库时独立执行。

## 游戏层

README 说明名称、平台／地区／版本、资料日期、分析范围、排除项、游玩形态／商业模式／运营方式、三层循环与系统地图。地图逐项链接正文，未查明的系统列查证办法。精确构建号未知就明确说明，别写“最新版”。

推荐目录：overview、systems、roles、assets。sources.json 或来源文档保存来源 ID、标题、URL、作者、日期、适用范围和限制；正文引用具体来源，不能只在最后列网站首页。

## 系统层

每篇达到模块专业设计文档深度：文档控制 → 目标边界 → 对象与术语 → 已核实事实 → 操作／机制图 → R-ID 规则规格 → 状态与异常 → 数据配置 → 系统接口 → UI/美术/音频状态 → 平衡与体验 → T-ID 验收 → 未核实项。库内详见 `_framework/模块专业设计文档标准.md`。

规则表写明条件、动作、状态／资源变化、可见反馈及证据；验收表使用给定条件、触发动作、预期结果并引用规则 ID。技术契约与原型演示值标 P，未知原作数值标 U。用例未运行就明确写未运行；不让专业格式掩盖证据缺口。

当用户要求可直接开发的参考版本时，每个模块说明可实施范围与不包含的内容；原作 U 与参考 P 分栏。配置给出可运行样例及合法域，依赖给出调用和返回契约，数值公式给出至少一个算例；所有影响成功、失败、资源、存档的分支必须有决策。共用事务、时间和数值约定可以集中成文，但各模块必须链接它并补充本模块例外。

每个事实有唯一 ID。推断说明由什么事实得到，在什么条件下失效；建议明确是新项目参考。成本／概率／效率没有测量不填精确数值。引用作者的攻略建议时保留其身份，官方转载不等于官方验证。

重点系统至少有解释规则的图。记录类型、图注、依据、来源和公开状态；使用截图前实际查看图片。原创机制图能解释规则，但不能验证原作布局、字体、操作手势或动效帧数。

## 岗位层

- 策划：循环位置、决策、资源、取舍、适用条件、验证实验。
- 开发：观察输入输出、参考实体／状态／事件、异常、恢复与测试；不得猜原作技术栈。
- 美术：原图观察、信息层级、反馈时序、状态矩阵、资产建议；尺寸与数量未知就待定。

三个岗位页链接同一系统正文，以阅读路径补充本岗要点；不拷贝三份正文。

## 检索层

有网页接入目标时，写稳定 gameId / systemId、主系统类型、已证实机制标签、路径、revision、关联案例、证据成熟度。未知属性为 null，不作为 false 或 0。收藏建议引用 systemId 与 revisionSeen。

可比较案例必须显示平台、日期、运营上下文及目标玩家。优秀程度按明确设计目标评价，不做没有量尺的总分。
