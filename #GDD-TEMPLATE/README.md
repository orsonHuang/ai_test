# GDD 规范 · 模板使用说明（README / INDEX）

> 本目录是一套完整 GDD 样例：《刃种农庄》（黑色幽默武器作物 roguelite，双循环玩法）。
> 本 README 从样例中提炼出**可复用的 GDD 规范**，用于：新项目从零写 GDD、旧 GDD 评审与补齐、AI 与人协作撰写设计文档。

## 规范一句话总结

**四阶段漏斗 + 决策/定稿分离 + 边界即契约 + 验证收尾。**

- 每个阶段只回答一个层次的问题，回答不了的显式推迟给下游。
- 每个"怎么想"（analysis）与"定了什么"（design）分开成对存放。
- 每份文档用"不做什么 / 不负责什么 / 本阶段不定什么"锁住边界。
- 每个粒度都以"P0 最小闭环 + 验证标准"收尾，闭环不成立禁止扩内容。

---

## 1. 总体结构：四阶段漏斗

| 阶段 | 目录 | 回答的问题 | 核心产出 | 对下游的约束物 |
|---|---|---|---|---|
| 00 概念 | `00_concept/` | 做什么？给谁玩？凭什么不可替代？明确不做什么？ | 核心幻想、目标用户、体验基调、"不是什么"表 | 末尾「概念定稿」段落 |
| 01 顶层 | `01_top_design/` | 以什么为单位循环？规模多大？哪些系统在范围内？ | 循环单位、规模锚点、循环图/资源流图、系统范围表、不做清单、验证标准 | 末尾「当前结论」段落 |
| 02 架构 | `02_architecture/` | 哪些系统支撑一轮玩法？系统间输入输出是什么？ | P0 系统清单（输入/输出/原因）、依赖图、数据流图、MVP 闭环 | 「目录映射」段落 |
| 03 系统 | `03_systems/` | 每个系统内部规则是什么？ | 每系统 design + analysis | 输出给执行层/数值表 |

**阶段间铁律：**

1. 下游不得违背上游定稿。要改，先回上游改 analysis（标记 superseded），再顺流更新。
2. 上游声明"本阶段不定"的内容（数值、命名、掉落率、UI），是下游的授权清单——只有下游可以定义，且只能定义一次（SSOT）。
3. 越往下游越具体，但任何阶段都不写实现代码和最终数值。

## 2. 目录与命名规范

```text
GDD/
├── README.md                    # 本文件：INDEX + 规范
├── 00_concept/
│   ├── analysis.md              # 决策记录
│   └── design.md                # 定稿
├── 01_top_design/
│   ├── analysis.md
│   └── design.md
├── 02_architecture/
│   ├── analysis.md
│   └── design.md
└── 03_systems/
    ├── S01_<系统名>/            # snake_case 英文目录名
    │   ├── analysis.md
    │   └── design.md
    ├── S02_<系统名>/
    └── S03_<系统名>/
```

命名规则：

- 阶段目录：两位序号 + 英文名（`00_concept`）。
- 系统目录：`S` + 两位序号 + `_` + 英文 snake_case（`S01_core_gameplay`）。
- 文档标题、正文一律中文；目录名、mermaid 节点 id 用英文。
- 系统拆分以 `02_architecture/design.md` 的「目录映射」为准，不得自行增删。

放置位置：项目内使用时放 `#PROJECT/<项目名>/GDD/`。

## 3. analysis.md 与 design.md 的分工

| 文件 | 性质 | 内容 | 判定标准 |
|---|---|---|---|
| `analysis.md` | 过程 | 围绕本阶段关键取舍的决策记录：候选方向 → 判断依据 → 结论 | 能回答"为什么不是另一个方案" |
| `design.md` | 结果 | 定稿结构：章节固定、结论先行、可直接指导下游 | 下游只读 design.md 即可开工 |

**两者必须配对出现**。只写 design 会让设计决策无法追溯；只写 analysis 则没有可执行定稿。

---

## 4. analysis.md 决策记录规范

文件由若干"问题块"组成，标题即问题（如 `## 问题：一天怎样形成清楚但不拖沓的双循环？`）。每块固定结构：

```markdown
## 问题：<一个具体的取舍问题>

状态：agent_proposal

### 广度分析
- <候选方向 A> 能提供 X，但会带来 Y。
- <候选方向 B> ……（每个候选一行，说清收益与代价）

### 深度分析
<判断标准与深层因果。哪条候选真正服务上游定稿？跑偏风险来自哪里？>

### 综合判断
<一句话结论，将被 design.md 直接采用。>
```

状态枚举：

| 状态 | 含义 |
|---|---|
| `agent_proposal` | AI 提案，等待用户确认 |
| `user_confirmed` | 用户已确认，design.md 可依据它定稿 |
| `superseded` | 已被推翻，注明日期、原因和新结论 |

规则：

1. 每个问题块必须显式对齐上游定稿，不得悄悄违背。
2. 广度分析至少列 3 个候选方向；不许只给单一选项制造伪比较。
3. 结论直接引用到 design.md 对应章节，两处表述一致。

## 5. design.md 分阶段必备章节

### 00_concept/design.md

| 章节 | 要求 |
|---|---|
| 一句话概念 | 一句话讲清题材 + 玩法 + 循环 + 长期期待 |
| 设计锚点 | 核心幻想 / 目标体验 / 玩家动机 / 核心循环 / 跑偏风险 / 非目标（每条一行） |
| 概念边界 | 声明本阶段只定什么、把什么推迟给 Top Design |
| 核心幻想 | 写出玩家脑中反复出现的那句话（引号内原话） |
| 目标用户 | 参照同类游戏受众描述，说明吸收什么、拒绝什么 |
| 玩家身份 | 用第二/三人称描述玩家是谁、每天在做什么 |
| 体验目标 | 第一人称列表（"我应该感到：1. 我不是…而是…"） |
| 情绪基调 | 含正向基调 + 边界（"可以…但不是…"） |
| 不是什么 | 表格：`不是 X | 原因`（≥5 行） |
| 概念定稿 | 一段收束语，显式约束 Top Design |

### 01_top_design/design.md

| 章节 | 要求 |
|---|---|
| 顶层定位 | 段落 + 一句玩家心声（引用格式） |
| 规模锚点表 | 循环单位 / 局外段时长 / 战斗时长 / 操作复杂度 / 经营复杂度 / 长期目标 / 长期期待 |
| 核心循环图 | mermaid `flowchart LR`，8-10 节点 |
| 完整循环图 | mermaid `flowchart TD`，展开资源与解锁分支 |
| 资源流图 | 谁产出什么、谁消耗什么 |
| 单循环流程表 | 阶段 \| 玩家行为 \| 设计目的 |
| 各段设计 | 每段一小节 + 顶层规则列表 |
| 失败与回收 | 表格：情况 \| 结果（明确"失败=少赚，不是毁档"） |
| 长期结构 | 编号列表 + 成长主轴优先级声明 |
| 系统范围表 | 系统 \| 顶层目的 \| Top Design 边界（每系统一行） |
| 不做清单 | 编号列表（≥5 条） |
| 验证标准表 | 验证点 \| 成功标准 |
| 当前结论 | 收束段，显式约束 Architecture |

### 02_architecture/design.md

| 章节 | 要求 |
|---|---|
| 架构定位 | 含相对上一版的变更与变更原因 |
| 一句话架构 | 一句话讲清闭环 |
| 总体闭环图 | mermaid |
| P0 系统清单 | 表：系统 \| 目的 \| 输入 \| 输出 \| P0 原因（每系统必须写"没有它会怎样"） |
| P1 / P2 边界 | 两张表：能力 \| 说明 |
| 系统依赖图 | mermaid `flowchart TD`；信息呈现类系统用虚线 `-.读取状态.->` 表示只读 |
| 数据流图 | mermaid |
| 系统职责说明 | 每系统一小节：负责什么 / **不负责什么** |
| 目录映射 | 目录 \| 本阶段定位（决定 03_systems 拆分） |
| MVP 最小闭环 | 编号列表（5-7 步）+ "闭环不成立则禁止增加 X" 声明 |
| 风险与校验 | 表：风险 \| 校验方式 |

架构铁律（样例验证有效）：

- **数据所有权唯一**：每个状态只有一个系统有权修改。
- **因果单向**：战斗只输出结果，不直接发放长期成长；奖励结算独立成系统。
- **呈现与规则分离**：信息呈现系统只读取状态，不做规则判断，不替玩家解题。

### 03_systems/<系统>/design.md

| 章节 | 要求 |
|---|---|
| 设计目的 | 开头声明"目的不是 X，而是 Y"，随后给**三种体验**（第一人称编号列表） |
| 系统范围 | 负责 / 不负责 两个清单（不负责 ≥4 条，覆盖相邻系统职责、数值、UI） |
| 核心循环图 | mermaid |
| 关键规则 | 每条规则带"设计理由"或"它解决的问题"；用表格给规则边界 |
| 状态与字段表 | 系统管理的实体状态：字段 \| 含义/用途 |
| 输出接口表 | 输出 \| 含义（对接下游系统的输入表） |
| P0 最小闭环 | 编号列表（5-8 步） |
| P1 / P2 后置表 | 优先级 \| 内容 \| 后置原因 |
| 验证标准表 | 目标 \| 验证问题 |

## 6. 通用模块与写作规范

**必用模块（各阶段按需取用）：**

| 模块 | 形式 | 作用 |
|---|---|---|
| "不是什么 / 不做清单 / 不负责" | 表格或列表 | 负面约束，防跑偏与职责泄漏 |
| "本阶段不定什么" | 段落或边界列 | 推迟声明，授权下游 |
| P0 / P1 / P2 分层 | 表格（含后置原因） | 范围控制，防止 MVP 膨胀 |
| MVP 最小闭环 | 编号步骤 | 最小可验证单元，是停止扩内容的闸门 |
| 验证标准 | 目标 \| 验证问题表 | 每个粒度的验收线 |
| 设计理由 | 跟随每条规则 | 说清 why，防止规则被无意推翻 |
| mermaid 图 | `flowchart LR/TD`，节点 `id["中文"]` | 循环、依赖、数据流 |

**写作规则：**

1. 中文短句；标题即结论或即问题。
2. 表格优先于段落；一条规则一行的列表优先于大段文字。
3. 玩家体验用第一人称写（"我打的每一仗都应该回溯到白天的种植选择"）。
4. 规则句式示范："只 X，不 Y"（如"铲除只释放地块，不返还资源"）。
5. 单个 design.md 控制在 200-300 行；超过说明本阶段塞了下游内容。

**禁止项：**

- 不写具体数值、掉落率、成长曲线、UI 布局（归数值表 / 执行文档）。
- 不写实现代码、不指定引擎 API。
- 不在下游偷偷定上游保留的内容。
- 不写"可能、也许、看情况"式无边界表述；要么定死，要么声明推迟并给 P 级。

## 7. 一致性契约链（评审清单）

任何一次 GDD 修订或评审，按此链逐条检查：

1. **上游一致性**：本文件是否违背任何上游定稿段（概念定稿 / 当前结论 / 目录映射）？
2. **接口咬合**：上游系统的「输出接口表」与下游系统的「输入」是否同名同义、无一遗漏？
3. **职责不重叠**：本系统"不负责"清单与相邻系统"负责"清单是否互斥？
4. **命名一致**：资源、状态、系统名在所有表格、mermaid 图、正文中是否同一写法？
5. **推迟兑现**：上游"本阶段不定"的每一项，是否恰好在某一下游被定义且只定义一次？
6. **闭环完整**：P0 最小闭环步骤是否覆盖了所有 P0 系统？验证标准是否可观测（问"玩家是否…"）？

## 8. 样例中验证有效的设计手法

写新 GDD 时可直接复用：

- **三种体验开头**：每个系统用 3 条第一人称体验声明目的，比抽象目标更可校验。
- **"它解决的问题"句式**：每个设施/机制一段，先说解决什么问题，再说边界。
- **考题式敌人**：敌人只考能力层（群攻/单点/爆发/控场），不做"某敌人对应某指定武器"的一对一钥匙。
- **奖励三级分层**：小怪=基础回流，普通 Boss=阶段推进，路线 Boss=重大突破（首杀保护）。
- **保护机制对抗挫败**：重大成就立即入档且不可被后续失败剥夺；失败只部分损失且比例可被成长改善。
- **撤退=下注而非逃跑**：固定撤退点 + 进入 Boss 后锁死，把回本判断变成核心张力。

## 9. 新项目落地流程

1. 复制本目录骨架到 `#PROJECT/<项目名>/GDD/`，清空样例正文（保留章节骨架）。
2. 按 00 → 01 → 02 → 03 顺序推进；每个阶段**先写完 analysis 全部问题块并拿到确认，再写 design**。
3. 02 完成后依「目录映射」建立 `03_systems/` 子目录；系统数量通常 3-8 个。
4. 每阶段收尾时跑第 7 节契约链检查。
5. GDD 定稿后再开数值表、执行文档；GDD 永远不承载最终数值。
