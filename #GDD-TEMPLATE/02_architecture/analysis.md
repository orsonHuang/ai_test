# 系统架构分析

## 问题：支撑一天闭环的最小系统边界是什么？

状态：agent_proposal

### 广度分析

- 把农场、战斗和成长写成一个大系统，初期简单，但责任和状态很快混杂。
- 按每种资源或操作拆小系统，边界清楚，却会产生过多接口和文档负担。
- 按玩家因果链拆分，可以让每个系统拥有明确输入、输出和失败责任。

### 深度分析

闭环中的关键责任是：日程触发跨天；农田与经济产出可出战作物；出战投入记录配置和消耗；路线战斗只输出过程结果；日结统一结算收益、损耗和农场变化；长期解锁处理品种线、设施与路线标记。

信息呈现应读取这些系统的状态，不替代它们做规则判断。战斗不直接发放长期成长，农田不定义武器攻击，日程也不处理奖励，这些边界能避免同一结论被多处维护。

### 综合判断

保留日程与跨天、农田与作物、水与基础经济、出战投入、路线夜战、日结与回流、长期解锁、信息呈现八项职责；实现时可组合服务，但数据所有权和因果顺序必须保持独立。

## 问题：怎样保留路线未知感，同时让玩家仍能规划并支持后续扩展？

状态：agent_proposal

### 广度分析

- 完整预告敌人、推荐配置和掉落最易规划，但会提前给出答案。
- 完全盲打保留惊喜，却容易让白天准备显得随意。
- 展示库存、成长状态、历史路线经验和有限线索，能提供依据而不泄题。
- MVP 直接做多路线能展示扩展性，但会在核心闭环验证前放大内容成本。

### 深度分析

玩家需要知道自身状态和既有经验，而不是知道下一晚的标准答案。信息系统应解释作物缺水、成熟时间、出战消耗、检查点和历史推进；路线中的具体敌人组合与奖励仍保留未知。

多路线、路线生态和最终 Boss 都依赖单路线的种植—出战—回流是否成立。架构只需保存检查点、路线通关和解锁槽位，不必提前实现节点地图。

### 综合判断

MVP 使用一条线性路线和有限状态信息验证闭环；通过稳定的路线结果、检查点与解锁接口预留多路线能力，但不恢复完整威胁预告，也不让未来结构进入当前核心范围。
